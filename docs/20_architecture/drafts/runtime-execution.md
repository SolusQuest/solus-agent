# Managed runtime execution draft

`SolusAgent.Runtime.Startup.RuntimeAgentFactory.Create(RuntimeConfiguration, RuntimeOptions?)` returns `IAgent`. Application startup selects the implementation and supplies live Host bindings; business orchestration needs only Api. Runtime owns each invocation's driver, classified records, attempt inventory, accepted model data and continuation. The independently compiled [Scripted Provider](../../../tests/ConsumerProbes/CustomProvider/ScriptedProvider.cs) references Runtime.Api alone. The [Runtime.Execution tests](../../../tests/SolusAgent.ContractTests/Runtime/Execution) compose it with the actual production Runtime; the existing M1 producers and Host consumers remain synthetic expressibility evidence.

```csharp
IAgent agent = RuntimeAgentFactory.Create(configuration,
    new RuntimeOptions(timeProvider: TimeProvider.System, requireContinuation: true));
AgentOutcome outcome = await agent.ExecuteAsync(request, progress, cancellationToken);
```

`configuration`, `request` and `progress` are Host-supplied values. This example does not supply transport credentials, tool authority or business acceptance. No dependency-injection framework, internal loop type, service locator or persistence format is required.

## Support and work meaning

The implementation advertises `WorkUnitLimit`, `DurationLimit`, `Cancellation`, `UsageReporting`, `DispatchLimits`, `UsageThresholds`, `ToolInvocationLimit` and `UsageAccounting`, plus `OrderedExposure` and `ProviderBounds`. Required outer capabilities are checked before progress, hooks or effects. Configured logical-call and physical-dispatch limits, input/output thresholds, tool invocation allowances and accounting policy are enforced even when the Host does not require their capabilities; null dimensions remain unconfigured. Provider count and numeric reservation admission are pre-exposure; thresholds stop subsequent model production. The [tool adapter](runtime-tools.md) independently reserves each complete batch before any member starts and projects immutable tool counts alongside provider token observations and accounting. Truthful nullable reporting does not promise complete measurements, hard token ceilings or billing accuracy.

Required runtime integration is validated at construction. Missing required hooks or required durable acknowledgement without hooks rejects with a safe configuration error. Absence of hooks is permitted only when ordered exposure is not required and the current request has no accounting policy. An active accounting policy requires hooks even with `RequiredGuarantees.None` and optional `UsageAccounting`: shared preflight returns `MissingHooks` before admitting an attempt or causing effects, mapped to Failed/ExecutionFailed (candidate ProductionFailed). A supplied hook is always honored. A profile requiring continuation selects `RuntimeOptions.RequireContinuation`; unavailable provider support rejects before effects and each provider request requires that semantics. `Describe` includes only support, numeric ceilings, closure allowance and closed configuration requirements, omitting provider/model labels, the clock and live bindings.

One completed work unit is one logical model response admitted against the actual runtime request. An attempt, dispatch or usage capture is not a completed unit. Default execution makes one physical attempt per logical turn. An explicit Host retry policy can permit additional physical attempts of the same logical call, without counting failed attempts as completed work. An accepted `Final` completes ordinary `ExecuteAsync`; `MaximumWorkUnits` is a ceiling, not a request to generate that many final responses. A valid tool-call response counts as one accepted logical response and enters the [runtime tool adapter](runtime-tools.md) only after provider settlement permits further admission. Its complete successful results feed the next bounded model turn; tools do not add model work units. The same runtime also implements explicitly selected `ICandidateAgent` through the [candidate driver](runtime-candidates.md); `IContextAgent` exposes the separately selected [ordinary context transition](context-envelope.md#production-ordinary-context-c1); tool/candidate restoration remains later work.

## Per-turn ordering and retained facts

The reusable `ProviderCallOperation` drives one logical call through complete physical `ProviderAttemptOperation` boundaries. Each boundary performs exposure permission, one provider invocation, observation retention, original-request response admission and same-attempt settlement; `RunState` owns request admission. `RunState.AdmitTurn` checks the current cut, completed-unit ceiling, configured logical-call and physical-dispatch limits, inventory capacity, available record slot and payload bounds before new effects. Its final admission commits a new logical identity, unique physical identity with ordinal one, inventory entry and physical-send reservation under the run cut gate before exposure. Count rejection adds no attempt and enters no hook or provider. All externally supplied `AgentInput` sources remain data; their source labels never authorize `FromModel`, Host instructions or tools. Only an admitted response becomes an accepted model record, anchored to its exact scope and attempt; required continuation remains with that turn without truncation or reinterpretation.

Logical admission, physical-send capacity, attempt inventory and completed work are separate. An admitted denied or failed call consumes logical capacity and remains in inventory without becoming completed work. Physical capacity is reserved before `BeforeDispatch`, including while permission is pending. Only the final sealed, association-checked observation can release that attempt's slot for confirmed `NotDispatched`, exactly once and independently of Host settlement delivery. `Dispatched` or `Unknown` retains the debit even with unavailable or zero measurements. The initial `NotDispatched` inventory placeholder is not refund evidence. Released slots do not release logical or inventory capacity. Candidate repair and accepted continuation start new logical calls; they are not retries. Exhaustion denies only subsequent provider production: an already accepted Final, its Host feedback, or an admitted tool batch can finish at the exact count boundary. A no-send accepted response can release capacity for later production without inventing a dispatch.

BeforeDispatch permission must match provider/model scope, execution/logical/physical IDs, ordinal and acknowledgement requirement. Null, failure, unknown, denial, mismatch or insufficient strength grants no dispatch. A final local admission cut follows the receipt. Every entered exposure receives one local settlement attempt, including denied or abandoned permission. An optional-hook-free path performs no invented Host acknowledgement. Host `Durable` remains its assertion, not a library storage certificate.

The [provider exchange draft](provider-exchange.md) now gives each single-use `ProviderRequest` its own `Observation`. The runtime can atomically `Seal` it independently of payload completion. Captured dispatch, usage and accounting before the cut survive; writers after it reject. Snapshots are immutable and sealing is idempotent. A faulting or absent interface result is normalized as an actually observed exchange failure, preserving current-channel facts. A foreign result becomes `Rejected/InvalidAssociation` without relabeling foreign usage. Associated returned observations can supply otherwise undisclosed facts before the local cut; conflicting streamed facts reject and retain the original capture.

`Accepted` on a returned response is insufficient: a forwarding interface could guard it under looser bounds or different continuation requirements. Runtime reuses `ProviderResponse.ValidateFor` against its actual request, retaining observation first. Invalid returned payload becomes a normalized rejected exchange, with no accepted record or completed unit. Missing usage remains unavailable, even when dispatch is known. Accepted work is recorded before settlement and progress, so later failure cannot erase it.

`RuntimeSettlement.ProviderInvoked` separates a seam that was never called from one still pending at a local cut. A pending invoked provider may have no obtained outcome/error while retaining known or unknown observations; only `Cancelled` or `DurationLimit` permits that state. An actual returned exchange or observed fault has a normalized outcome/error. Never-invoked closure has NotDispatched/unavailable measurement and an explicit admission stop. Settlement delivery status never occupies the original stop field.

## Deadline, cancellation and completion

One injected monotonic clock measures the whole-run local deadline, including input admission, exposure, provider waiting and normal closure. Every start and response acceptance shares a run-owned gate with the cut. Caller cancellation wins when it is already observable at that cut; otherwise reaching the deadline closes admission. At an exact deadline, a ready permission or response cannot override the cut. Once a cut is observed its cause is retained. This is a local observation/linearization rule, not a real-time scheduling or remote-stop promise.

The cut seals the active observation immediately, wakes the wait and signals extension cancellation asynchronously. It does not wait for uncooperative cancellation registrations. Held asynchronous exposure/provider operations cannot delay local termination; late receipts, results, observations or faults have no path to new admission or returned snapshots. Faults of abandoned tasks are observed. Trusted in-process extensions must bound their own synchronous invocation/property/observer work and allocations; the runtime cannot preempt synchronously blocking code, reclaim a remote operation or forcibly remove references held by an extension.

Settlement uses the same clock with a finite allowance: normally the smaller of remaining run time and `SettlementGrace`; after a cut, at most one explicit `SettlementGrace` is available for closure. The default is one second and the configurable maximum is thirty seconds. Thus execution admission ends at the requested duration, while an uncooperative cleanup callback can extend terminal return by at most the configured post-cut allowance, subject to local scheduling. This allowance grants only closure, never another provider/tool/candidate effect. Late Continue cannot reopen admission.

Terminal precedence is pre-work unsupported capability; then an observed caller/deadline cut; then exposure/provider/bounds/closure failures; then the response handler and ordinary progress. Denial returns Partial. Invalid association, observed provider failure and uncertain closure delivery return Failed; payload/capacity limits return ResourceLimit. A valid correlated settlement Stop closes further admission while an already accepted Final still completes. For a nonterminal handoff, Stop or missing/failed/unknown/mismatched closure prevents the next turn. A progress exception is separately `ProgressObserverFailed`, preserving accepted units and usage. Cancellation observed during final progress prevents completion without erasing that unit. No terminal result is later rewritten by abandoned work.

### Token thresholds at next production

`RunState` derives checked per-dimension token observations from its validated immutable attempt inventory, as specified in the [usage draft](usage.md#checked-run-token-observations). `InputTokenThreshold` and `OutputTokenThreshold` compare only their configured axes before the next model attempt, after existing cut/work/attempt/record and logical-call/physical-dispatch admission checks. A known exhausted count remains ResourceLimit even if token comparison is incomplete. At least one complete reached comparison yields ResourceLimit; otherwise a required incomplete or overflowed comparison yields Partial. Reporting-only missing counters do not stop work. Known NotDispatched contributes no consumption without falsifying the original missing measurement. Overflow stays explicit and cannot prevent returning the individual attempts.

The token check does not close admission while handling the current accepted response. Its tool batch or candidate delivery may finish subject to existing cuts, capacities and Host closure; only the next model production is denied. Ordinary Final and correlated candidate Accept/End can complete even at/above a threshold or with unknown usage, while Reject/End retains HostEnded/Partial. Candidate Continue checks the same preflight before correction append, and actual admission checks again. The candidate `UsageAccountingUnavailable` category maps to Partial and distinguishes missing required comparisons from Host integration Stop. The default token behavior above is extended only by the explicit accounting policy below; retry admission uses the same comparisons, while billing calculations remain outside this leaf.

### Accounting transition and precedence table

The current request's [accounting policy](usage.md#host-accounting-policy-and-authoritative-ledger) creates a private per-invocation ledger. The final admission gate commits the numeric reservation together with logical/physical slots and attempt inventory. `BeforeDispatchAsync` sees that reservation and the derived balance before any provider effect. Its receipt must match the entire numeric snapshot as well as existing scope, attempt and required strength. The initial inventory placeholder never releases numeric or physical reservation.

| Trigger / phase | Runtime numeric transition | Host exchange and next admission |
| --- | --- | --- |
| Invalid policy / incompatible required guarantee | Reject at request construction; no attempt or numeric reservation | No effects |
| Active policy, missing hooks (even with no required runtime guarantees) | `MissingHooks`; empty ledger/inventory | No provider, tool, candidate or progress effect; no invented receipt |
| New production preflight | Cut and integration check, then count/work/capacity; complete reached token threshold or numeric insufficiency/overflow before required unknown comparison | Denial creates no attempt; candidate correction is appended only after this preflight |
| Atomic admission / pending permission | Both dimensions `Reserved`, sharing the same attempt as count reservations | Correlated numeric disclosure; no provider effect until valid permission and final cut |
| Permission denied, missing, wrong, failed, weak or cut before provider invocation | Final `NotDispatched` releases both numeric dimensions and the physical slot once; logical/inventory entry remains | Closure retains original admission stop; late permission cannot dispatch |
| Known dispatched core dimension | Replace its estimate with exact `Measured`; release unused estimate, retain overrun | Independent peer dimension follows its own measurement availability |
| Missing core dimension after known/possible dispatch | Stop/ContinueUnknown: `Unresolved`; ConservativeCharge: estimate becomes only `ConservativeCharge` | Required unknown comparison stops under Stop; alternatives remain subject to explicit count/duration and allowance admission |
| Measured overrun or aggregate overflow | Preserve exact entries and negative remainder or explicit per-axis Overflow | Existing Final/tool/candidate End may finish; next production cannot admit insufficient/overflowed accounting |
| Final observation retained, Host settlement pending/failed/unknown/wrong | Ledger is already finalized; no rollback, second charge or second release | Post-settlement snapshot must match; uncertain closure prevents further effects |
| Local cut / delayed provider or Host completion | Keep sealed observations and settled/unresolved numeric evidence | Bounded closure allowance only; late callbacks cannot rewrite returned snapshots or reopen admission |

Finalization is once per full admitted attempt; a duplicate equal final observation is idempotent and a conflicting repeat rejects before state mutation. Provider `UsageAccounting` claims remain in observations but never debit or release this ledger. Each immutable `RuntimeSettlement.Accounting` is created after local settlement and before Host delivery; `SettlementAcknowledgement.Assess(RuntimeSettlement)` verifies that post-state in addition to the original exposure. Legacy exposure-only receipts remain valid for no-accounting execution but cannot acknowledge active accounting. Equal execution GUIDs in simultaneous invocations do not share any accounting state. All storage is run-local and bounded by the existing attempt capacity.

## Explicit provider retries

The Host requests retries through `AgentRequest.UsageLimits.RetryPolicy`. Null preserves one physical attempt; `new AgentRetryPolicy(3, backoff: TimeSpan.FromSeconds(1))` permits at most three attempts including the first. The immutable draft validates 1–64 attempts, nonnegative fixed backoff, and a nonnegative Host `MaximumDelay` no greater than ten minutes, with backoff no greater than that ceiling. Unspecified backoff is zero; unspecified ceiling is ten minutes. This permission is implemented by the managed runtime and does not assert support by arbitrary `IAgent` implementations.

Both positive R1 `Transient` and `Throttled` classifications are eligible. `ProviderFailed` alone, arbitrary interface exceptions, cancellation, rejected payloads, foreign scope/identity, conflicting observations and uncertain closure do not grant eligibility. The associated normalized `Failed/ProviderFailed` result must survive observation validation, local ledger settlement and every installed Host closure gate before its metadata reaches the logical-call operation. An installed settlement hook must acknowledge the exact exposure and final accounting with Continue; Stop or missing/failed/unknown/mismatched delivery forbids retry. Legitimate absent optional hooks neither create a receipt nor block otherwise authorized retries; any active accounting policy still requires hooks before admission.

A retry preserves execution/logical IDs, original classified input and completed tool history, tool definitions, scope, required semantics, response bounds and exact continuation. It creates a fresh single-use request/observation, fresh physical ID and the next consecutive ordinal. The latest physical attempt must already be finalized and unaccepted. No failed response or failure text is appended as model history. All failed/unknown exposure and per-axis accounting remain in the same bounded inventory and ledger; known NotDispatched can release only its own numeric and physical reservation, once. Reversed legal historical accounting inventory remains valid, while the currently reserved attempt stays last.

Before waiting and again before admission, the runtime checks the original cut, integration, work, inventory, records, physical capacity, token thresholds and accounting balance. Only a second logical-call debit/check is omitted. Existing count and known-limit priority over required unknown comparisons remains. No tool-invocation allowance is consumed by retry itself. Accepted work, tool handling and candidate Host delivery happen only after the successful physical attempt closes; handlers receive that successful attempt's actual request. Exhausted retry permission or a permanent failure retains Failed and all prior observations; a retry denied by run capacity or required accounting uses the existing ResourceLimit or Partial categories.

Backoff uses the run's injected monotonic `TimeProvider` and interruption gate. Waiting, provider execution and normal Host closure all consume the original deadline; cancellation does not wait for an uncooperative cancellation callback to release the delay. With `HonorRetryAfter=false` (default), provider hints are not admitted. With it enabled, an admitted hint within `MaximumDelay` produces `max(Backoff, hint)`; a larger hint declines retry and preserves the failed exchange rather than dispatching early. Zero delay still passes the cut and admission gates. No attempt, tool or candidate starts at/after the cut, and late failures/Continue receipts cannot reopen admission or mutate returned usage. Settlement grace remains closure-only.

The retry tests exercise both public runtime entrypoints, finite/default/permanent failures, full association and ordinal negatives, no-send refunds, missing-usage policies, numeric overflow, fresh permission and settlement barriers, controlled backoff and hint boundaries, uncooperative cancellation callbacks, held late provider results, progress failures and equal-execution-ID isolation. Mixed tool/candidate tests compare actual classified histories and continuation origins, including correction metamorphism and exact once-only effects. These are synthetic production-runtime checks, not live provider interoperability, billing or remote-stop proof.

## Finite state and next leaves

| Dimension | Policy |
| --- | --- |
| Initial classified inputs and each provider request | `ProviderExchangeBounds.MaximumInputs`; one Host instruction consumes a slot |
| Whole-run input/model/tool-result records | `RuntimeOptions.MaximumRecords`, default and ceiling 64; reserve a response slot before exposure |
| Whole-run attempt inventory | `MaximumAttempts`, default and ceiling 64; independent of completed units and measurement availability |
| Logical provider calls | Optional `AgentRequest.UsageLimits.MaximumLogicalCalls`; charged on admission, including denied/failed calls |
| Possible physical sends | Optional `MaximumPhysicalDispatches`; reserve before exposure, release only on final confirmed `NotDispatched`; inventory capacity still applies |
| Retained variable input/definition/model/tool-result bytes | `MaximumRetainedBytes`, default and ceiling 196608; strict provider payload accounting, no wire-size claim |
| Response and continuation | Configuration ceilings, with response ceiling lowered to remaining retention capacity |
| Time | Current `AgentRequest.Bounds.MaximumDuration`, plus only the explicit bounded closure allowance |

Capacities never scale allocation with an arbitrary Host work allowance. No compaction or silent truncation occurs. Immutable snapshots preserve complete attempt inventory even when individual measurements remain unavailable. Concurrent calls, including equal Host execution IDs, allocate independent records, logical/physical IDs, observation channels and cuts; no run lookup or permission cache exists on the shared agent.

The internal turn operation returns accepted data, normalized provider facts, local stop and settlement status only after closure. Its real two-turn tests demonstrate continuation replay, work/inventory admission, and non-vacuous Stop/unknown gating. The public driver handles Final and admitted ToolCalls through the actual generic batch operation. The [candidate driver](runtime-candidates.md) reuses the same provider operation for Final-response feedback; these leaves include no unused public handler framework. Public ordinary/candidate tests also prove independent count dimensions, last-slot/next-denied behavior, no-send slot reuse, denied/failed inventory, cancellation and equal-execution-ID isolation; direct state tests verify repeated refund cannot release another attempt's numeric or physical reservation. Token thresholds and explicit accounting compose with these checks. Explicit provider retries now compose with that same state; restoration remains M4 and packaging/migration M5. The optional DeepSeek adapter owns its separate transport proof. No live/paid run, storage certification, product acceptance or release support is established here.

Use [project validation](../../00_project/validation.md) for focused and full checks. Tests use explicit barriers and a controlled clock, and require local terminal return before releasing held operations. They cover original-request substitution, phase cross-products, boundaries, same-identity isolation and ordinary-data canary confinement through actual Runtime code.

## Ordinary context and renewed execution rounds

`ExecuteWithContextAsync` uses the same ordinary driver and admission/settlement operations as `ExecuteAsync`. The codec validates structure and request associations before the Host consumes its exclusive round grant. Only trusted, exclusively claimed state reaches provider import/materialization; a failed import consumes the grant and never dispatches work. A fresh run cut and new ledger then begin. Current bindings, required guarantees, retry policy and allowance remain authoritative. A continued logical operation carries its exact predecessor through `ProviderHistory.OperationOrigin`; accepted historical Final records carry exact origins through `ProviderHistory.AcceptedOrigins`. This explicit validated lineage permits foreign-execution history without treating arbitrary foreign model records as accepted.

The saved ordinary retry cursor is a real classified provider failure with retained positive usage and acknowledged closure, stopped before another safe attempt. Continuation waits under current retry/backoff policy and new duration, preserves original request semantics and advances its global physical-attempt ordinal. Its automatic retry count is relative to the new round. An accepted and safely closed Final supports a new Host-requested task instead. A cancellation/deadline stop during resumed backoff, before any new attempt, retains the inherited pending cursor, original bounds, provider state and exact predecessor for another explicitly authorized round. Captured uncertainty remains inspectable and blocked. Rejected admission enters no execution, exposure, provider dispatch, progress or capture path.

Current-round work, logical calls, physical sends, tool allowance, thresholds and accounting reservations renew; total retained inventory and storage capacities do not. Prior rounds remain immutable and separately inspectable. Historical Final records retain their own effective request bounds, while current live definitions occupy cumulative byte capacity. Terminal stop and elapsed duration are frozen before provider export. Terminal capture is independent of work/closure/progress outcome, and sink failure cannot erase known consumption or accepted work. See the [context draft](context-envelope.md#production-ordinary-context-c1) for exact supported states, provider/Host obligations and process-restart evidence limits.
