# Provider exchange draft

`SolusAgent.Runtime.Api.Providers` supplies a bounded in-memory M1 extension seam for the self-owned runtime. The separately compiled [CustomProvider producer and Host consumer](../../../tests/ConsumerProbes/CustomProvider/ProviderProbe.cs) has Runtime.Api as its sole direct production reference, no packages, and no Runtime or downstream source. It uses the accepted [Tools](function-tools.md) and [Usage](usage.md) vocabulary through Runtime.Api's existing references. Api and Tools.Api retain their independent boundaries. The optional [DeepSeek provider](deepseek-provider.md) now implements this seam with bounded HTTP projection/parsing and a selected service profile. This seam and its synthetic fixture do not deliver a production loop, budget engine, saved-state codec or distribution.

## Host control and model data

`ProviderRequest` retains exact `ProviderScope` provider/model labels and `ProviderAttempt` execution/logical/physical correlations with a positive logical-call ordinal. Scope has no endpoint, credentials or transport configuration. The Host allocates distinct physical identities for attempts, including retries; an accepted earlier logical call cannot be represented again as the next call. Attempt inventory validation uses the existing `AgentRunUsage`, rather than a new provider ledger or retry policy.

`ProviderInput` factories keep Host instructions, untrusted input, accepted model data and actual `ToolResult` data in separate immutable positions. Host instructions are initial entries only. Calling the instruction factory asserts Host authority; it does not authenticate the source or make this an in-process sandbox. Products must never call it on model, repository, restored or tool data. Responses have no instruction, endpoint, tool-definition or capability members. A requested tool name only asks for an already Host-supplied definition; payload text cannot enlarge that set or grant permission. The [security boundary](../security-boundary.md) applies to callers and later projection.

Host definitions are immutable `ToolDescriptor` values with unique ordinal-exact names. Responses use exact `ToolCall` associations and Host tool schemas/byte limits; duplicate, recycled, unknown or malformed calls reject. The accepted closed scalar tool profile is retained completely. Descriptive metadata grants no authority. The test-only Host uniquely resolves and prepares every batch member and checks every concrete narrow capability before the first invocation. A later member's domain or capability rejection leaves all members undispatched. This synthetic path is evidence for batch admission, not a public executor or production scheduler.

Prior model turns enter input only through guard-accepted `ProviderResponse` values. Request validation rejects cross-scope/run association, repeated physical or completed logical identities, conflicting/recycled call IDs, unsolicited/duplicate/mismatched results and incomplete tool rounds before the next input/model turn or dispatch. Results match `ToolCall.Matches`, including tool name and exact raw arguments; reordered results remain correctly associated. Tools' guarded success/failure results can both remain data. A ToolResult does not authorize retry or prove rollback.

## Response acceptance and continuation

The current `ProviderFinish.Final` shape requires nonempty text and zero calls. `ToolCalls` requires a nonempty batch and permits accompanying model text. These are reversible draft choices, not universal wire finish reasons. Undefined or conflicting shapes reject explicitly. Candidate construction is not request-relative acceptance: the `ModelProvider` guard validates scope, every attempt field, supported call association/schema, configured limits and continuation semantics. It returns an internally accepted immutable copy only on success. Rejected candidates and their continuation cannot enter replay history.

`ProviderContinuation` owns bounded opaque bytes, exact provider/model scope and originating attempt. It never decodes, trims, reconstructs or interprets hidden reasoning. `CopyReplayBytes()` is an explicit restricted-consumption operation returning a fresh copy. Modifying the source or a replay copy cannot change retained state. The latest accepted model turn determines the next request's required replay: missing, orphan, wrong-scope, stale-anchor or altered bytes reject. A deliberate fresh conversation remains a separate Host choice; silent fallback is absent. This is in-memory association, not authentication, durable compatibility or a restoration codec.

The finite synthetic exchange emits two correlated calls and continuation, invokes both tools with Host capability after complete admission, sends results in reversed order, replays the exact required token and accepts final model data. A separate provider failure variant captures valid usage before constructing or admitting an invalid response. The tests use synthetic canaries, never live continuation or downstream source.

## Observation, cancellation and failure

`IModelProvider` expresses one attempt; `ModelProvider` supplies the guarded subclass seam. `ProviderObservation` is bound to that request's immutable attempt, starts with `DispatchExposure.Unknown` on admitted core entry and carries no payload text. Implementers report known dispatch before awaiting measurement where known and call `CaptureUsage` once before later payload validation. It reuses `UsageAttemptObservation` exposure/measurement/accounting invariants. Known dispatch cannot regress and a captured observation cannot be replaced; contradictory or duplicate reports fail without erasing the first valid capture. Capture closes under a lock on every core return or throw. Late writers reject rather than changing returned evidence. Producers must await their observation work before returning.

`ProviderExchangeResult.Observation` retains normalized usage/exposure independently of accepted payload. Unsupported required capabilities and pre-cancellation refuse core invocation with known NotDispatched/Unavailable evidence. Unexpected core failure preserves Unknown unless dispatch was explicitly observed. Unknown or unavailable is never filled with zero; independent conservative accounting claims do not become measurement. Positive measured consumption requires Dispatched. UsageReporting promises honest nullable retention, not complete counts or enforcement.

The guard closes capture before candidate admission. Constructor, association, schema, byte-limit or payload rejection returns a fixed error with retained usage and no response. Unexpected exceptions return ProviderFailed without their messages. A matching caller-token cancellation returns Cancelled; unrelated cancellation exceptions are failures. Cancellation is checked after core completion and immediately before publishing an accepted response; that final check is the acceptance cut. Cancellation observed before the cut prevents success and retains captured evidence. After the cut it cannot rewrite the immutable success. Cancellation, rejection and failure imply neither remote stop, settlement, rollback nor retry authority.

`ProviderCapabilities` advertises complete tool exchange, exact continuation and honest usage reporting separately. Requests include explicit requirements plus those implied by their represented tools/replay. An unsupported requirement refuses core invocation. A provider may emit continuation only when the request explicitly requires continuation support; the resulting token is then required if that accepted turn is continued. There is no lossy adaptation or alternate provider selection.

## Finite retention and diagnostics

| Dimension | Draft ceiling |
| --- | --- |
| Exact provider/model label | 128 UTF-8 bytes each, nonempty, no control characters |
| Classified inputs | 32 |
| Host definitions / calls per turn | 16 each |
| One instruction/input/model text | 16384 strict UTF-8 bytes |
| Opaque continuation | 8192 bytes, nonempty |
| Aggregate request payload | 131072 bytes |
| Aggregate response payload | 65536 bytes |

`ProviderExchangeBounds` can lower its exposed exchange ceilings. Counts are checked before defensive copies; text is admitted before encoding/retention and byte input before strict decoding. Checked aggregate accounting includes variable scope labels, text, historical responses/calls/results, descriptor names/descriptions/capability IDs/schemas, and retained replay bytes/scope labels. Fixed-size GUID, enum and count metadata is separately bounded by finite collection counts; these totals are in-memory payload measures, not wire-size or token estimates. Tools.Api still owns its own leaf limits. Producers must also bound allocations before constructing values; the contract is not hostile-code isolation.

Payload-bearing `ToString()` methods return type names. `ProviderDiagnostic` is the explicitly ordinary, serializable diagnostic surface: correlation GUIDs, positive ordinal, closed outcome/error/exposure/completeness and accepted-call count. It contains no provider/model labels, input/output, call IDs/arguments/results, continuation or exception details. Request, response, continuation and `ProviderExchangeResult.Response` are restricted payloads; arbitrary serialization or logging of those objects is not an ordinary diagnostic route. The Host owns visibility, storage and protection.

[Providers tests](../../../tests/SolusAgent.ContractTests/Providers) run the actual producer/consumer and guard, including all-member admission, invalid associations/shapes, replay requiredness/ownership, known and unknown dispatch, cancellation cut neighbors, captured usage after later failures, concurrent capture separation, capture closure, immutable input/call snapshots, finite count/byte boundaries and diagnostic canaries. Evaluated Architecture tests prove the actual CustomProvider boundary and preserved production graph. [Project validation](../../00_project/validation.md) owns focused/full commands and evidence limits.

The optional DeepSeek adapter proves selected projection, strict parsing, raw usage mapping, restricted replay and controlled transport behavior through its own tests; none follows from these synthetic seam values. Its owning document bounds credential injection, HTTP send and diagnostics evidence; remote stop, streaming and live service interoperability remain unproved. M3 owns production enforcement/accounting and M4 owns complete restoration and durable integrity/compatibility. Live or paid calls require their own authorization; ordinary CI remains secret-free.
