# Runtime tools draft

The production Runtime consumes Host-installed `IFunctionTool` bindings through one metadata-driven adapter. Public `RuntimeAgentFactory.Create` / `IAgent.ExecuteAsync` runs accepted tool-call responses, their guarded results and subsequent model turns, and the separately selected [candidate driver](runtime-candidates.md) runs the same operation between its bounded provider turns and Final candidate submissions. Independently compiled [CounterTool](../../../tests/ConsumerProbes/CustomTools/CounterTool.cs) and interface-only [TransformTool](../../../tests/ConsumerProbes/CustomTools/TransformTool.cs) exercise this same operation with different schemas and capabilities. There is no per-name product mapping, new assembly or package.

## Complete admission before effects

A tool-call response must first pass original-request provider admission and same-attempt settlement. Stop, failed/unknown/missing closure, cancellation or deadline cannot grant a tool effect. Resolve each exact unique name from the captured Host registry and compare the tool's current full descriptor semantics with that registration; equivalent immutable descriptors need not share object identity.

Before the first invocation, check the entire finite batch's actual input schemas, effect-free Prepare result and exact prepared call, then call [ValidateInvocation](function-tools.md#preparation-and-authority) against every actual supplied narrow capability. Concrete type and exact capability semantics both matter. Preparation and admission cannot manufacture authority or probe permission by executing a later member. Unsupported schemas reject at the real sealed schema parser; only the full closed scalar object profile is supported. Trusted in-process extension getters and validation must bound their own synchronous work and remain effect-free; this is no hostile-code sandbox.

Reserve all tool-result record slots and the finite member inventory before invocation. The retained-byte check includes each exact repeated call association plus that descriptor's maximum result bytes. This deliberately conservative policy may refuse eventual small outputs that would fit: it guarantees room for every valid admitted result rather than truncating after effects. Actual accepted results consume actual bytes; unused allowance is not charged into the next turn. RuntimeOptions caps whole-run records, attempts and retained bytes independently of an arbitrarily large Host work ceiling.

## Sequential effects and truthful partial records

`AgentUsageLimits.MaximumToolInvocations` adds an optional positive run-level allowance. Null preserves the existing behavior and finite runtime capacities. `AgentCapability.ToolInvocationLimit` independently advertises complete-batch enforcement; the production factory supports it on both ordinary and candidate execution. Other implementations must reject it when required unless they enforce it. Tool allowance does not replace model work units, provider attempts, candidate submissions, repairs or continuations.

After every member passes preparation/capability checks and the complete batch fits record/byte capacity, reserve its entire invocation count before any tool starts. Admission requires the whole batch to fit the remaining run allowance; an affordable prefix is never executed. The provider turn that produced a refused batch remains accepted model work with its own retained attempt and usage.

Entering `IFunctionTool.InvokeAsync` through the run cut gate converts one reservation into an irreversible invoked count. This measures interface entry, including synchronous faults, guard rejection, failed effects and uncertain noncooperative work. It does not assert that the guarded core ran or a business effect occurred: `ToolResult.InvocationStarted` retains that distinct guarded-core meaning. Every exit from an admitted batch releases only its members still proved unstarted, including after cancellation when the execution gate is closed. No release refunds an entered invocation or authorizes replay.

`AgentRunUsage.ToolInvocations` is an immutable optional `ToolInvocationUsage` snapshot, separate from provider inventory coverage and token measurements. `Invoked` counts entries; `ReservedUnstarted` counts currently held reservations; `ReleasedUnstarted` cumulatively counts admitted members never entered whose reservations were released. A runtime run reports known zeros before any tool batch. A producer lacking tool knowledge leaves the observation null. Terminal outcomes are projected after batch cleanup, so a two-member batch cut during its first invocation reports 1 invoked, 0 reserved and 1 released. Late success or fault cannot change it. Ordinary progress retains its existing successful-turn reporting points and projects the same tool facts; no new terminal progress notification is promised. Earlier progress snapshots remain unchanged when a later batch is interrupted.

Invoke admitted members in provider order. Each start and result commit shares the run's cancellation/deadline gate. Invocation rechecks capability and atomically claims its owner-bound prepared handle; preflight grants no lasting permission. Tools add no model work units. A work ceiling of one therefore allows the admitted first turn's tool batch, then refuses a second model turn: ordinary `ExecuteAsync` reports ResourceLimit, while candidate execution reports the literal `WorkUnitLimit`.

Restricted run-owned member records initially mark every member Unstarted. Entering an interface invocation marks the current member InvokedUnknown. Each obtained guarded result is revalidated against the exact requested call and actual registered result schema/size, immediately classified as ToolResultData, and recorded with its fixed outcome/error and InvocationStarted observation. Failure, cancellation or output rejection cannot erase earlier success or enable retry; remaining members stay Unstarted.

A null, thrown, foreign or loosely guarded invalid interface result supplies no valid associated ToolResultData. Its current member retains fixed failure/rejection and unknown effects rather than an invented result. A held noncooperative invocation at the local cut remains InvokedUnknown, with no false zero-effect claim. The runtime returns without releasing or waiting for that extension; late results and observed late faults cannot rewrite snapshots or start another member. A tool-reported Cancelled without an actual caller/deadline cut produces outer Failed rather than fabricating caller cancellation. Actual caller cancellation returns Cancelled; duration/capacity returns ResourceLimit, preserving accepted model units and usage.

## Complete next turn and confinement

Only a complete successful batch enters the next provider turn. ProviderInput preserves the accepted model and exact associated tool results as data, with the latest required continuation unchanged. ProviderRequest rejects missing, duplicate, foreign, recycled, wrong-name or changed-raw-argument associations before the next provider effect. Complete results may be reordered by exact identity; the runtime itself invokes and records provider order. Record/input/request-byte/work/attempt limits stop further admission while preserving completed tool effects.

Each execution allocates independent records, cuts, prepared handles and provider identities, including equal Host execution IDs. Hosts may deliberately share a capability object; Runtime neither clones that authority nor caches permission between runs. Outcomes, progress and startup disclosure remain numeric/closed ordinary metadata. Arguments, success JSON, capabilities, continuation and raw exception details remain restricted internal/provider data. The separately requested [context capture channel](context-envelope.md#completed-tool-history-r1) can retain completed or partial tool facts; ordinary progress/results expose no journal, payload or rollback certificate.

## Completed history restoration (M4-R1)

The ordinary context driver retains accepted ToolCalls, their original effective bounds, each original descriptor/call/member ordinal, actual results and partial states, committed record order and a next-provider cursor. A resumable completed batch requires acknowledged provider closure and every successful result committed before the next provider effect. Restoration validates complete chronology and current bindings, then materializes historical results through Tools.Api without preparing or invoking tools. The next actual provider turn sees original associations and continuation; historical invocation counts remain in `History`, and current invocation counts begin at zero. New calls still require whole-batch admission and current permissions.

The actual current-result guard rejects `ToolResult.IsHistorical`, including interface-only tools that return a perfectly matching imported result. Interface entry is still honestly counted; rejection neither invents a core effect nor refunds the entry. Partial, failed, rejected, unstarted and invoked-unknown members can be captured with their real facts, but R1 never advances or retries them. Missing interface results remain missing. Partial-member recovery belongs to R2, and candidate context belongs to its separate leaf.

## Evidence and limits

[Runtime.Tools tests](../../../tests/SolusAgent.ContractTests/Runtime/Tools) primarily exercise actual public startup and ExecuteAsync with independent producers, effect counters and request-inspecting Scripted Provider. Supplemental tests inspect the same internal production batch operation's retained success/failed/unknown/unstarted snapshots. They cover multiple real tool rounds, all-member rejection, schema/result forwarding, exact count/byte/capacity neighbors, replay, bounded noncooperative waits, late faults, progress failure and concurrent-run confinement. The [Runtime/Consumption](../../../tests/SolusAgent.ContractTests/Runtime/Consumption) tests run the same operation inside mixed tool/candidate production episodes under both business Hosts. [Project validation](../../00_project/validation.md) owns the actual commands.

The tool-allowance tests add public ordinary/candidate exact-limit and whole-batch rejection, cumulative admission, held cancellation/deadline cuts, immutable public progress/outcome snapshots, same-ID overlapping runs and invocation-entry failure cases. Internal operation checks additionally observe in-flight reservations and idempotent cleanup. Candidate tests separate tool counts from model work and follow-on allowances. RuntimeConfiguration and Usage checks cover independent capability requirements and tool knowledge without fabricated provider metrics.

Tools.Api and Api remain independent; CustomTools references Tools.Api alone and CustomProvider Runtime.Api alone. Existing Final/permission/closure/usage tests and M1 fixtures keep their original evidence identities. CompletedToolContextTests, ToolContextTransitionTests, PartialToolContextTests and real CompletedToolProcessTests prove R1's actual public context path, exact associations, safe boundaries, current controls, cumulative capacity and no repeated completed effects. These unreleased drafts supply no automatic tool retry, durable receipts, partial/candidate restoration, production storage, product acceptance, live/paid calls or package qualification. The optional DeepSeek adapter's controlled transport evidence is separate.
