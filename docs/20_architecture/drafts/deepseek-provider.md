# DeepSeek provider draft

`SolusAgent.Providers.DeepSeek` is an optional, callable `ModelProvider` implementation. Its sole direct production reference is `SolusAgent.Runtime.Api`; it has no package dependencies or Runtime reference. The four core libraries retain their reference graph. This implementation projects, sends, reads and admits one actual HTTP exchange through the [provider exchange draft](provider-exchange.md). The bounded [provider-turn runtime](runtime-execution.md) is separately implemented; the generic [runtime tool adapter](runtime-tools.md) owns complete tool rounds. The separate [candidate driver](runtime-candidates.md) owns Final-response feedback with tool rounds composed inside its productions. Budget enforcement, durable restoration, distribution and downstream migration retain their delivery boundaries.

## Selected service profile

The Host constructs `DeepSeekOptions` with a credential and a positive `maximumTokens` from 1 through 393216. The only endpoint is exactly `https://api.deepseek.com/chat/completions`, and the provider/model scope is `deepseek` / `deepseek-flash`. Options do not look up environment variables, files or alternate backends. The request always selects `model=deepseek-flash`, `stream=false`, `thinking.type=enabled`, `reasoning_effort=high` and the supplied finite `max_tokens`. It omits optional sampling and tool-choice features.

The official [thinking guide](https://api-docs.deepseek.com/guides/thinking_mode/) and [chat completion API](https://api-docs.deepseek.com/api/create-chat-completion/) were checked on 2026-10-08. The implementation admits this selected profile; synthetic fixtures and local TLS do not establish live interoperability or billing accuracy. Request model selection and response model identity are independent checks. Only response `model=deepseek-flash` is accepted; legacy or neighboring aliases fail rather than being inferred from the requested model.

## Projection and tool association

Requests require at least one input. Classified Host instructions become `system`, input data becomes `user`, accepted model data becomes `assistant`, and correlated tool result data becomes `tool`. Content, raw tool argument strings, call IDs, result strings and ordering are preserved. Null assistant content stays null. The entire normalized Tools.Api scalar input schema is emitted as function parameters for every registered tool. Tool capabilities, result schemas and result text never become instruction authority. A failed guarded tool result is represented as fixed outcome/error data.

The provider proposes calls; the Host still prepares, admits and invokes tools with its own capabilities. Successful `tool_calls` requires a nonempty call batch. The Runtime.Api guard rejects unknown tools, duplicate or recycled historical call IDs, invalid input schemas and request-relative count/byte violations before a response becomes eligible for history. Successful `stop` requires nonempty text and no calls. `length`, `content_filter`, `insufficient_system_resource`, `aborted`, unknown, missing and null finishes reject even if text or arguments look complete. No partial response becomes a final candidate or invocation authority.

## Restricted in-run replay

Any request with tools explicitly requires the Continuation capability before its first send. Every historical accepted assistant turn must retain its own exact `reasoning_content`, including empty strings and final turns with no calls. Replay decodes each turn separately, while Runtime.Api checks the latest continuation's exact scope and originating attempt. Missing, malformed, wrong-scope or stale replay rejects before transport; there is no silent fresh-conversation fallback.

The internal token is one discriminator byte followed by strict UTF-8 reasoning. Empty reasoning therefore has a nonempty token. The 8192-byte M1 ceiling includes that byte, allowing at most 8191 reasoning bytes; lower request bounds also apply. Unknown frames and invalid UTF-8 reject. Text-only requests can decline continuation retention; subsequently introducing tools into history without the required tokens fails explicitly. This framing is an in-memory adapter detail, with no durable codec, authentication or cross-process compatibility claim. Continuation, inputs, outputs and tool payloads are restricted data under [Security boundary](../security-boundary.md).

## Bounds and admission

Logical M1 bounds and wire bounds are separate. The request writer caps escaped JSON while writing, before dispatch. Options default to 1048576 request-body bytes and 524288 response-body bytes; both are positive, lowerable and at most 1048576. The response reader checks declared length, reads incrementally with a one-byte overflow probe and rejects truncated declared lengths. It disposes requests, responses and streams on all outcomes.

Admission requires strict UTF-8 JSON with depth at most 16, no comments or trailing commas, no duplicate decoded property names, and valid Unicode strings. The root must identify a nonempty bounded completion ID, `object=chat.completion` and the separately admitted model. Exactly one choice with index zero and assistant message is supported. Streaming deltas, legacy `function_call`, multimodal content, unsupported fields and conflicting finish/call shapes reject. JSON content type is required, with absent or UTF-8 charset and no content encoding. Payload constructors and the base guard impose the M1 absolute and lowered request bounds after parsing.

## Usage and failure retention

Unique nonnegative lexical Int64 `prompt_tokens` and `completion_tokens` become nullable input/output measurements. Missing counters stay unknown; `total_tokens` never fabricates either core counter. Direct cache hit/miss are input subsets; reasoning tokens are an output subset. `prompt_tokens_details.cached_tokens` is an equivalent cache-hit source, never an additional count. Unknown parents remain unknown. Conflicting aliases, invalid subsets, cache partitions or totals reject the payload while retaining independently valid core facts and dropping untrustworthy detail claims. No CacheWrite measurement is fabricated.

Usage capture occurs before identity, finish and payload admission. A bounded, parseable HTTP error body may provide independently valid usage, but error status never produces success. A known non-200 status keeps ProviderFailed precedence when its body is oversized, truncated or unreadable; attributable caller cancellation remains a separate outcome. Duplicate usage envelopes yield unavailable measurement. Malformed complete JSON, invalid raw UTF-8, oversized or interrupted bodies cannot supply validated counters. A later rejection or cancellation preserves already captured usage and exposure. Ordinary outcomes and diagnostics contain fixed classifications rather than provider error text or exceptions.

## One attempt and transport diagnostics

The default path owns a fresh `SocketsHttpHandler` and `HttpMessageInvoker` per attempt. It uses exact HTTP/1.1, a nonnull known-length POST body, `ExpectContinue=false` and `Connection: close`. Redirects, proxy, cookies, automatic authentication and decompression are disabled. Body serialization is allowed once. The selected .NET 10 handler policy excludes pooled reuse, HTTP/2 or HTTP/3 retry/downgrade and the empty/delayed-body premature-EOF retry path. The adapter contains no retry loop. A retry requires a separately admitted attempt with new Host-owned correlation and accounting.

`ActivityHeadersPropagator=null` excludes the request/header-publishing diagnostics handler. An inner guard replaces transport exceptions before invoker telemetry observes them. Standard System.Net EventSource, DiagnosticListener and ActivityListener canary tests verify the ordinary diagnostic boundary. Privileged `Private.InternalDiagnostics` raw tracing and arbitrary in-process Host code remain trusted capabilities, outside that boundary.

The overload accepting a terminal `HttpMessageHandler` is for Host-controlled transport. Delegating handlers, HttpClientHandler and known unsafe SocketsHttpHandler policies are rejected. Arbitrary executable handlers must honor one-send and restricted-data rules themselves; the adapter does not sandbox their code or logging. Disposal closes owned resources and makes subsequent calls fail before dispatch; it does not assert remote stop or rollback.

Preparation and pre-send cancellation are NotDispatched. Entry to `SendAsync` is Unknown until a response proves Dispatched; a thrown send cannot prove no exposure. Caller cancellation reaches send/read and produces the caller's cancellation classification only for exceptions carrying that supplied token. An unrelated or absent exception token remains provider failure even when the caller concurrently cancels. The positive options timeout defaults to 120 seconds, is at most ten minutes, and produces provider failure if the caller did not cancel. Local cancellation or timeout does not prove that remote work stopped. Overlapping exchanges use independent bodies, observations and correlations.

## Closed retry classification

The actual adapter produces the [provider result seam's](provider-exchange.md#closed-retry-classification) safe optional retry metadata without scheduling or resending. Its finite HTTP allowlist is 429 (`Throttled`) and 408, 500, 502, 503, 504 (`Transient`). All other statuses, including authorization/input errors, redirects and non-allowlisted 5xx, remain unclassified `ProviderFailed`. Positive status classification requires a bounded complete valid UTF-8 JSON body, admitted content headers and valid measurement syntax; the error body need not have a successful completion shape. Malformed, oversized, truncated, unreadable, encoded or otherwise locally invalid error bodies keep existing `ProviderFailed` precedence with no positive classification. Independently validated usage already captured before later validation failure remains retained.

Transport classification occurs inside the sanitizing handler before the HTTP invoker can observe raw exceptions. Only typed `HttpRequestError.ConnectionError` and `ResponseEnded` without an attached HTTP status are transient; DNS, TLS/authentication, protocol, unsupported/unknown categories and generic exceptions are unclassified. An exception's attached status cannot bypass the actual-response validation rule. Message text and inner-exception text are never classification evidence. An attributable adapter-owned deadline expiration during transport is transient; matching caller cancellation remains Cancelled, and unrelated cancellation exceptions remain unclassified failure. A typed interrupted successful-status body can retain transient transport classification; an unreadable error-status body follows the conservative status rule above. Disposal, request/response/association/continuation/encoding/bound rejection cannot acquire eligibility from `ProviderFailed` alone.

For eligible status failures only, a single valid `Retry-After` delta-seconds or HTTP-date can provide an advisory delay from zero through ten minutes inclusive. HTTP dates use receiver UTC, not the response's Date header. Missing, malformed, duplicate/conflicting, negative, expired, overflowing or excessive hints omit only the delay; the independently validated status classification remains unchanged. Hints on successful or ineligible outcomes are omitted and cannot create eligibility. The adapter never sleeps; ordinary caller and whole-run deadline authority remains unchanged. Classification does not prove safe replay, remote stop, known-zero usage or permission for another send. Controlled tests exercise actual adapter/guard/independent consumer paths, every allowlisted status and transport neighbors, hint boundaries, retained usage, standard telemetry confinement and production Runtime stopping after one attempt.

## Invocation-owned observation

Each `ProviderRequest` is single-use for guarded exchange and owns its numeric `Observation`. Reusing an already invoked or presealed request fails without a second transport call and preserves its sealed evidence. The runtime can snapshot and atomically seal that channel at its local cut independently of a held HTTP operation. The adapter checks the active observation channel before send and reports obtained dispatch and usage through that same channel. Sealing rejects later observation reports; the runtime's separate commit gate excludes results after its local cut. Sealing alone is not a general payload-admission barrier and never implies that an already started remote operation stopped.

`ObservationIntegrationTests` execute the actual adapter with the merged Runtime.Api guard. They cover presealed and repeated requests, external sealing while send or body read remains held, exclusion of late response/usage, idempotent snapshots and retained valid forwarding-transport measurements. The shared runner also references Runtime for its separately owned runtime tests; the adapter assembly and its direct project graph remain independent of Runtime.

`RetryCompositionTests` additionally connects actual 503/429 parsing to the production retry operation during one mixed tool/candidate run. Transparent observation checks the full execution/logical/physical/ordinal association independently of wire equality, fresh observation channels and continuation origins from the successful physical attempt. `RetryAccountingCompositionTests` exercises actual HTTP-derived known, zero, missing and partial measurements plus typed send/body response loss under Stop, ConservativeCharge and ContinueUnknown through both public runtime entrypoints. It checks per-axis reservations, final dispositions and next-admission snapshots, default/finite/exhausted retry permission, permanent and malformed/unreadable error neighbors, retained safe usage after later invalid model/finish content, physical/inventory/threshold/accounting boundaries, known-limit priority, refused closure and fresh retry permission. Denied permission can leave an additional NotDispatched inventory entry without another HTTP send; admitted attempts, transport sends and tool invocation-interface counts are asserted separately from business effects. `RetryCutCompositionTests` uses a controlled monotonic clock and real-operation barriers for fixed backoff, admitted/ignored Retry-After, above-ceiling hints, the original whole-run deadline, cancellation and held failure settlement. Retried send/body cuts retain earlier tool effects, acknowledged candidate receipts and settled per-attempt accounting. Each held producer or hook is released only after the local terminal result where applicable, then observed to actual completion before checking that returned snapshots and effects remain unchanged.

This composition proves production wiring, selected accounting policies and provider-only retry enforcement under synthetic transport with an Api-only Host and synthetic fixtures. It does not exercise live DeepSeek service access, billing accuracy, remote stop, durable context restoration or product migration, and it involves no provider secret or paid call. The scripted Host and controlled transport remain test fixtures, not production Host or transport implementations. The runtime and candidate drafts own the production semantics; this draft owns only the adapter behavior they compose.

## Provider-owned persistence and admission

`DeepSeekProvider` implements `IProviderContextPersistence` through the existing Runtime.Api seam. The ordinary runtime retains exact classified history, original response bounds and each accepted turn's opaque continuation. DeepSeek exports a compatibility and consistency witness for that exact binding; it does not replace history with a hash or duplicate reasoning. A legal 8192-byte replay remains exportable because the witness has a separate fixed size. Export and admission perform no HTTP, tool invocation, storage or registration and retain no hidden session cache or dispatch permission.

The sole current provider `FormatVersion` is 1. Its payload is exactly 36 bytes: ASCII `DSCP` followed by a 32-byte SHA-256 commitment; there is no additional version byte. The committed sequence uses .NET `BinaryWriter` UTF-8 strings with their 7-bit encoded byte-length prefixes, little-endian Int32/Int64 values, a one-byte Boolean and `Guid.ToByteArray()`'s 16-byte representation. In order, it contains the string `deepseek-flash-thinking-high-context-v1`, endpoint string, maximum tokens, request-body cap, response-body cap, timeout ticks, binding provider/model strings, binding execution/logical/physical GUIDs and attempt number, then continuation presence. When present, continuation provider/model strings, its own execution/logical/physical GUIDs and attempt number, Int32 replay length and exact framed replay bytes follow. This domain identifies the current thinking-enabled/high, nonstreaming model profile. Credentials, handlers, live clients, delegates and build identities are excluded.

Export requires the installed exact provider/model scope and, when present, a valid discriminator-1 strict UTF-8 replay. Unsupported binding or disposed adapter returns null. Admission requires the exact current format, payload length/header, saved scope/checkpoint origin, valid replay and fixed-time equality with the current commitment. Unknown, truncated, trailing, corrupt or foreign state rejects. Checkpoint origin and continuation origin are bound separately: a failed attempt, including in a later round, must not replace the earlier accepted replay origin. The runtime and trusted Host own complete historical-lineage admission; the narrow provider binding cannot authenticate history by itself.

Compatibility requires exact endpoint/model/profile, `MaximumTokens`, both wire caps and timeout. This conservative current-draft rule rejects changed output or transport policies before sending. A freshly supplied credential and compatible terminal handler may differ; neither is persisted. Repository SHA equality is neither sufficient nor required. There are no historical readers, migrations, provider conversion or silent fresh fallback. The witness checks consistency, not authenticity: Host provenance and exclusive round admission remain mandatory. Under C1, the trusted Host claim precedes provider admission; provider rejection prevents dispatch and does not refund that claim. A direct consumer must honor the admission result rather than treating import as a mutable lock on arbitrary later calls.

`PersistenceProcessTests` launches separate processes with fresh adapter/handler instances and injected synthetic credentials through public C1 runtime startup. It captures a tools-enabled ordinary Final without executing tools, then restores exact reasoning/history into a new Host task and compares the complete actual next HTTP body with independently constructed expected JSON. Empty and maximum legal replay are covered. A controlled 503 resumes the same operation with new execution/physical identities and a higher attempt number. Three processes cover an earlier accepted Final, a failed new task and later retry, preserving earlier reasoning while binding the later checkpoint origin. Historical usage remains separate from current-round usage. Format, origin, model, corrupt payload, replay and configuration neighbors reject with zero sends; trusted synthetic malformed selections distinguish preclaim rejection from actual provider admission rejection. A compatible retry after configuration rejection also proves the claim was consumed. Restricted checkpoint/wire files deliberately contain synthetic continuation; ordinary results, stdout and errors do not.

`PersistenceWireTests` separately executes real multi-call tool results with reversed legal result order, null assistant content, exact Unicode/whitespace arguments, empty reasoning and subsequent Final reasoning. It exports state, disposes producing adapters and imports into a fresh adapter/handler before checking the complete actual next wire request and response association. Only original immutable accepted carriers are reused in that process; no old tool is invoked to manufacture history. This is direct adapter replay fidelity, not cross-process executed-tool reconstruction: C1's public `ToolResult` has no effect-free restoration factory. Production completed-tool restoration and mixed tool/candidate process composition retain their independent delivery boundaries. No live service, real credential, durable-storage qualification or billing claim follows from these controlled tests.
