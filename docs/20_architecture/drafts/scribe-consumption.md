# Scribe consumption draft

An Api-only Scribe-shaped synthetic business Host consumes the accepted outer drafts end to end: it explicitly starts fresh from validated business progress and exchanges independently correlated candidates with bounded repair and honest uncertainty. The independently compiled [ScribeHost](../../../tests/ConsumerProbes/ScribeHost/ScribeHost.csproj) library has `SolusAgent.Api` as its sole production reference, no packages, and compile inputs confined to its own project directory. The runner's [ConsumerProbes/Scribe](../../../tests/SolusAgent.ContractTests/ConsumerProbes/Scribe) startup composes it with the existing scripted candidate producer, the actual CustomProvider configuration provider/hooks/consumer/tool fixtures and the independent scripted usage producer, and the [Runtime/Consumption](../../../tests/SolusAgent.ContractTests/Runtime/Consumption) startup composes the same Host with the actual production runtime. Business checkpoint and campaign accounting, domain evidence and patches, storage and external effects stay outside the shared contracts; the Host owns no agent loop, and a budget engine, real provider transport, restoration codec, packaging and downstream migration remain unproved.

## Fresh reconstruction from validated progress

`ScribeManifest` records the ordered member tokens selected for one Host task. `ScribeProgress` retains only minimal validated facts after acceptance, and derives unresolved members from the manifest selection. Synthetic validation covers exactly three checks: a fact must name a selected member, must not repeat an already accepted member, and must carry valid bounded fact text. These checks demonstrate synthetic validation only; they establish no product checkpoint enforcement or M7 target identity.

The Host explicitly constructs `ContextExecutionRequest` with `ContextExecutionIntent.Fresh` and a null envelope from its current trusted instructions, requested bounds and required capabilities. The manifest selection, each accepted fact and each unresolved member are reconstructed as separate classified `AgentInput` data entries, so accepted facts are data for the producer rather than regeneration assignments, and unresolved work is distinguished from accepted facts. The test startup consumes that exact request before deriving `CandidateExecutionRequest`; supplied-context intent is unsupported in this adapter and is never silently downgraded to fresh. A second fresh invocation uses a new execution identity with new protocol identities and a new usage scope, reconstructs the same validated facts and produces only remaining work. No envelope, transcript or runtime context is stored or carried in business progress, and this Host choice does not weaken the selected complete runtime restoration requirement. Instruction-like fact text stays classified data and cannot change current Host control, installed bindings or validation.

## Independent candidates and bounded repair

The Host supplies `ICandidateHost` domain acceptance over a tiny synthetic payload grammar. It validates and commits each submission before any delivery, then performs its scripted exchange, so business progress can contain a fact the agent never observed as accepted. Rejection retains nothing and delivers correction data through a tiny correction grammar carrying a marker and an optional requested fact. A production following a rejection is a repair: it consumes that correction as untrusted data and the correction causally determines the repair content. Missing, marker-less or malformed correction data never authorizes fabricating a repair; the production reports failure and submits nothing.

The executed matrix covers accepted-first with rejected-second while work remains, accepted-first with rejected-second plus one admitted fresh failed repair of the rejected candidate and a denied next repair, and a repaired candidate accepted to end the run without additional production, with the accepted fact proven equal to the correction-derived text and distinct from any pre-scripted value. A metamorphic pair shows changed correction data changing repair content accordingly, and a counterexample shows rejection without repair data producing no repair candidate or submission. Earlier accepted progress survives rejection, missing feedback, explicit unknown feedback and cancellation of a held acknowledgement. Repair submissions carry the rejected submission identity, repair admissions stay within the finite candidate limits, and the terminal categories remain literal: Host-ended, missing and unknown delivery are partial, submission, work-unit and repair exhaustion are resource limits, held-then-cancelled observation is cancelled with an unknown pending receipt, and exposure-blocked production is production failure rather than a repair limit. Correction-derived text remains untrusted data that cannot change Host control, installed bindings or validation. A completed scripted run never establishes manifest completion; the Host calculates coverage separately, and no candidate result implies patches, storage or publication.

## Runtime startup, exposure and settlement

Inside representative candidate production callbacks the startup instantiates the actual `ConfigurationProvider`, `ConfigurationHooks`, `ConfigurationConsumer` and installed `ConfigurationTool` with its narrow capability. The consumer performs exposure, permission, provider dispatch and same-attempt settlement; the startup production path then performs real guarded tool preparation and invocation against the correlated provider calls. Preparation is effect-free, invocation uses the installed narrow capability and preserves call association, and provider or model data cannot select bindings.

Only a correlated acknowledged settlement receipt permitting continuation can authorize the downstream tool and candidate work. Missing, unknown, failed, mismatched and explicit Stop settlement all block tool invocation, candidate production and submission on the actual production path while the real dispatched attempt and measured usage stay retained; earlier accepted progress survives and cancellation remains cancellation rather than a settlement failure.

A valid exposure acknowledgement precedes any provider effect and settlement carries full same-attempt identity. A held acknowledgement proves zero dispatch before permission, while denied, missing and unknown exposure fail closed with the stopped attempt projection retained separately. Honest usage survives candidate rejection: the known provider observation stays known and a no-measurement neighbor stays unavailable rather than becoming zero. Unknown settlement retains the dispatched observation and stops that consumer's later admission. An explicit retry shares its logical identity with a new physical attempt, its own exposure and its own closure; no automatic retry or scheduler exists.

## Independent usage observations

The existing scripted usage producer and Host consumer run independently over the Host-owned current inputs, reporting progress snapshots and terminal usage with known measurements plus unavailable, partial and failure-after-dispatch neighbors. Each producer observes only its own seam: candidate outcomes disclose null usage honestly, runtime attempt observations stay in the restricted startup records, and no surface aggregates or double counts the separate candidate, runtime and usage scenarios.

## Restricted diagnostics

Ordinary surfaces — serialized `CandidateExecutionResult` and receipts, `AgentProgress`, `AgentOutcome`, `RuntimeAttemptDiagnostic`, `RuntimeConfiguration.Describe()` and safe `ToString()` projections — exclude candidate payloads, correction text, reconstructed progress facts, provider model text, provider continuation replay bytes and fake provider, hook and tool credentials. The restricted startup channel deliberately inspects the exact synthetic provider continuation when relevant; it holds no live material.

## Production runtime composition (M2)

The same `ScribeBusinessHost` drives the actual production runtime through its minimal Api-only fresh candidate-injection method. The startup layer composes `RuntimeAgentFactory.Create` over a `RuntimeConfiguration` carrying the independently compiled ScriptedProvider and the narrow CustomTools `CounterTool` and `TransformTool` bindings, then hands the returned `ICandidateAgent` face to the Host. `ExecuteFreshCandidatesAsync` internally consumes the Host's own `CreateFreshRequest` through the existing `ScribeCandidateStartup.Adopt` adapter and runs the candidate exchange against the Host's own `SubmitAsync`; no runtime type, transcript, continuation or saved state crosses the Api boundary. One invocation runs the mixed production `ToolCalls` → Final Reject → correction-derived Final accepted with `Continue` → `ToolCalls` → Final accepted with `End`, so five accepted model responses and two real tool batches drive three submissions with one repair and one continuation. Tool output causally determines the accepted facts, the Host correction causally determines the repair fact, and changed correction data changes that repair.

The following matches the tested composition in `ScribeHostRunsFiveTurnToolCandidateMixedProductionInOneFreshInvocation`; `steps` is the finite independent ScriptedProvider script and `exchangePlan` is the Host's own scripted policy list. The snippet runs in the managed runner's Runtime/Consumption test context with the `SolusAgent.Api.Candidates`, `SolusAgent.Api.Execution`, `SolusAgent.Runtime.Api.Configuration`, `SolusAgent.Runtime.Startup` and `SolusAgent.ConsumerProbes.ScribeHost` namespaces imported alongside the implicit `System` namespaces.

```csharp
IAgent agent = RuntimeAgentFactory.Create(
    new RuntimeConfiguration(provider,
        [new RuntimeToolRegistration(counter, counterCapability), new RuntimeToolRegistration(transform, transformCapability)],
        hooks),
    new RuntimeOptions(requireContinuation: true));
var host = new ScribeBusinessHost(manifest, new ScribeProgress(manifest, []), control, exchangePlan);
var result = await host.ExecuteFreshCandidatesAsync((ICandidateAgent)agent, progress, cancellationToken);
```

A second fresh invocation is a lifecycle choice, not restoration: it reconstructs only validated facts and unresolved members under a new execution identity with fresh protocol identities and fresh run usage, which `ScribeSecondFreshRunUsesNewIdentitiesWithoutTranscriptOrRestoration` checks against the exact reconstructed request. Committed Host progress and Runtime acknowledgements stay distinct: a validated fact committed before a held delivery survives a cut as committed progress even when the receipt is `Unknown`, and that uncertain delivery is never replayed, which `HeldHostAcknowledgementReturnsAtCutAndKeepsCommittedFactsWithoutReplay` witnesses through the completed late delivery. Host coverage is calculated separately from runtime completion and `ExternalEffects` stays zero.

## Limits and later activation

This probe's M1 tier proves contract consumption through synthetic producers and fixtures only; its M2 tier proves that the same Host drives the actual production runtime and tool batches through one mixed production, with the ScriptedProvider still standing in for real transport. Product acceptance and full M7 behavior, real checkpoint or campaign accounting, domain evidence and patches, storage and external effects, production budget enforcement, real provider transport and adapters for this business Host (the generic candidate-host composition over controlled DeepSeek transport is published with #35 in pull request #41), complete runtime restoration and its codec, packaging and downstream migration all remain unproved and belong to their own milestones. The Host's fresh choice is a product-side lifecycle decision that never weakens the self-owned runtime's restoration requirement. Activation of those later obligations requires the roadmap milestones and their own evidence, not this consumption proof.
