# Prepared function-tool draft

`SolusAgent.Tools.Api` supplies an executable M1 draft for bounded function-tool metadata, actual argument validation, effect-free preparation and explicit capability-authorized invocation. The compiled synthetic [CustomTools consumer](../../../tests/ConsumerProbes/CustomTools/CounterTool.cs) depends on Tools.Api alone. Tools.Api remains runtime-independent; the separate [runtime tools draft](runtime-tools.md) owns live registration consumption, generic batch scheduling and restricted recording. Retry, tool transport, product effects and package distribution remain outside this leaf.

## Supported metadata and schema

`ToolDescriptor` is immutable. Tool names, capability semantic identifiers and schema property names use `[a-z][a-z0-9_]{0,63}` and ordinal exact comparison. Noncanonical values reject rather than being folded into another identity. Descriptive `ReadOnly` and `Mutating` values grant no execution authority; unknown effect values reject. Descriptions admit at most 1024 UTF-8 source bytes before trimming outer whitespace and reject empty normalized text. Opaque call IDs retain exact spelling and whitespace, reject control characters, and admit at most 128 UTF-8 bytes.

`ToolSchema` supports the `bounded_closed_object` profile. The root is a nonnullable object; objects at every level declare `properties` and `additionalProperties: false`. Required names must be unique declared properties; omitted `required` normalizes explicitly to `[]`. Optional absence and a present null remain distinct. Nested values support closed objects, homogeneous arrays, strings, booleans and signed Int64 integers. A nested type can be paired with `null` using a two-entry type array; other unions, null-only types, references, open objects and unsupported keywords reject. This is a deliberately bounded subset, not general JSON Schema.

Integers support inclusive `minimum`/`maximum`, and admit exact mathematically integral decimal/exponent spellings within Int64 and the field's range. `ToolInteger.TryParse` reads a single bounded JSON number token for actual tool producers without floating-point rounding or changing raw call identity. It returns false for whitespace, malformed syntax/encoding, fractions, overflow and oversized tokens; null is a caller precondition error. Long mantissas and exponents require work proportional to bounded token length, never numerical exponent magnitude. `1`, `1.00` and `1e0` have the same numeric value but remain different raw call associations. Consumer domain hooks and deserializers must deliberately read these semantics; lexical `GetInt64` extraction alone is insufficient.

Strings optionally declare a nonempty ordinal-distinct `enum`; null can appear only for a nullable string and must be an explicit enum member to pass. Arrays require an `items` schema, with optional integral `minItems`/`maxItems` between zero and 1000 and minimum no greater than maximum. Normalization emits the intrinsic defaults zero and 1000. Integer bounds, enum values, nested closure, item constraints, requiredness and nullability survive deterministic normalization and reparse; type-irrelevant or unknown constraints never disappear. The [JSON Schema validation vocabulary](https://json-schema.org/draft/2020-12/json-schema-validation) supplies the bounded precedent for these keywords; the profile intentionally adds finite Int64 and structural ceilings and rejects all unimplemented vocabulary.

| Dimension | Ceiling |
| --- | --- |
| Schema source and normalized UTF-8 bytes, independently | 8192 each |
| Declared properties per object / across the schema | 32 / 128 |
| Semantic schema nodes, including root and array items | 256 |
| Semantic object/array container depth | 6 |
| Schema-syntax JSON container depth / member occurrences / aggregate array elements | 18 / 1024 / 256 |
| String enum entries, including null | 32 |
| Argument or success-result UTF-8 bytes | 16384, or the smaller descriptor limit |
| Payload JSON container depth / aggregate member occurrences | 6 / 2048 |
| Payload elements per array / across all arrays | 1000 / 1024 |

All independent limits apply; their maxima are not promised simultaneously. Count decoded member occurrences across all objects, while detecting duplicate names within each object. Charge every scalar, null and container array element once in its parent, plus any elements inside nested arrays. Semantic schema nodes and declared properties are distinct from schema-syntax containers and keywords. Strict JSON admits no comments, trailing commas, duplicate decoded names or malformed Unicode. Syntax/depth/duplicate errors remain `InvalidJson`, count/byte excess is `LimitExceeded`, and unsupported schema semantics is `UnsupportedSchema`.

Byte factories admit size before strict UTF-8 decoding; string entrypoints check strict UTF-8 byte count and reject malformed UTF-16 before parsing. Payloads use owned immutable strings, so caller byte-array mutation or document disposal cannot change a prepared call. Producers must also bound their own allocations before creating output. Supporting a request for 800 lines does not promise an 800-line result: independent complete-result bytes, including metadata, can reject it. Products own any declared truncation policy; the schema and runtime do not silently clip results.

An integration must verify support for the complete profile, property semantics, result boundary, effect description and capability semantics before adapting a descriptor. It must reject unsupported semantics rather than silently omit constraints or treat a similarly named built-in tool as equivalent.

## Experimental revision after internal.1

This source revision replaces the `closed_scalar_object` profile and lexical-only integer semantics from the immutable `0.1.0-internal.1` packages. Flat scalar schema documents remain expressible under the new profile, but integrations must update their explicit support checks and numeric readers. Runtime tool-bearing context bindings include descriptor/profile semantics; an older incompatible binding rejects explicitly, with no old-profile alias, converter or silent fresh fallback. Same-revision restoration remains supported through current Host authority. The [experimental package policy](../../10_workflow/package-consumption.md) promises no upgrade compatibility: a future authorized immutable version requires exact consumer pinning and revalidation and must never replace published `.1` bytes.

## Preparation and authority

Consumers use `IFunctionTool`; implementations can derive from `FunctionTool<TCapability>` or delegate through an interface-only wrapper, as the independently compiled TransformTool does. `Prepare` checks the actual call tool name and real arguments against every supported input constraint, then runs optional effect-free implementation-local validation. It returns `ToolPreparation` with either a fixed rejection or an owner-bound `PreparedToolInvocation` retaining the exact bounded original call. No capability is supplied or invoked during preparation. Trusted tool code must not perform effects in its validation hook; this library is not a sandbox for hostile in-process implementations.

`ValidateInvocation(prepared, expectedCall, capability)` checks the actual owner, full call, concrete capability type, exact semantic ID and unused-handle state without effects or claiming the handle. The generic guard shares these actual binding checks with invocation. Batch consumers check every member before any invocation; ID equality alone is insufficient. The result grants no lasting authority: invocation rechecks the binding, cancellation and atomic claim. Trusted interface implementations must uphold the same effect-free contract.

Preparation is not execution permission. The host separately supplies a narrow capability at invocation. The guard verifies both the concrete required capability type and its exact semantic identifier. A capability must confine the actual effect; the model, descriptor, prepared handle and argument data cannot manufacture trusted authority. The synthetic counter capability exposes only a counter mutation and cancellation token, without generic service lookup, process, network, filesystem or platform clients.

`InvokeAsync` checks the actual tool instance, full expected call association (call ID, tool name and exact raw arguments), explicit capability and cancellation before dispatch. A different owner, ID, name, arguments, or missing/wrong capability rejects before effects. An already-cancelled request returns Cancelled before effects. These refusals leave the prepared handle available for a later explicit authorized attempt. After admission, an atomic claim permits at most one dispatch per handle, including concurrent callers; failure or cancellation after that claim does not enable replay. The host still owns uniqueness across separately prepared handles and runs. This local guard is not a durable or distributed exactly-once effect guarantee.

## Output, cancellation and failures

The tool produces `ToolOutput` carrying the original call association plus bounded raw success JSON or a fixed failure. The guard checks output association before success acceptance, then enforces the selected result size/schema. The final `ToolResult` is associated with the requested call and exposes `InvocationStarted`. Non-success outcomes contain no success JSON; errors use fixed `ToolError` values and never publish arbitrary exception details. `ToString` on payload-bearing contracts returns a type name rather than payload contents.

Preparation and pre-dispatch rejection can be shown to have zero effects. Result rejection, failure and in-flight cancellation can happen after an effect. `InvocationStarted: true` explicitly preserves that uncertainty and does not imply rollback, product acceptance, or retry authority. Matching supplied-token cancellation is Cancelled; unrelated cancellation exceptions are Failed. A validated successful output is preserved when cancellation is signalled after completion. An abrupt process death supplies no promised final result.

| Boundary | Result |
| --- | --- |
| Invalid metadata, encoding, schema or retained payload size | Classified `ToolContractException`; no prepared invocation is retained. |
| Invalid descriptor limit configuration or null API argument | `ArgumentOutOfRangeException` or `ArgumentNullException`; these are caller precondition errors. |
| Invalid actual arguments or effect-free domain rejection | Rejected `ToolPreparation`, with no effects. |
| Owner/call mismatch, denied capability or used handle | Associated Rejected result before dispatch. |
| Pre-dispatch cancellation | Associated Cancelled, `InvocationStarted: false`. |
| Invalid, oversized or mismatched output | Associated Rejected, `InvocationStarted: true`; effects may have occurred. |
| Implementation failure or matching in-flight cancellation | Associated Failed or Cancelled, with honest dispatch observation. |
| Accepted associated bounded output | Succeeded with the validated success JSON. |

## Historical result admission (M4-R1)

`ToolResult.RestoreHistorical` is the supported effect-free reconstruction seam for independently trusted historical facts. The caller supplies the original descriptor, original call and recorded call/result fields. Admission checks exact ID/name/raw-argument association, supported input/result schema and byte boundaries, defined outcome/error codes and coherent `InvocationStarted`/JSON combinations. Success requires a started invocation, `None` and valid success JSON; non-success has a fixed error and no success JSON. Cancellation preserves whether the guarded core started. Reachable guarded rejection and implementation-failure facts remain representable without implying rollback or retry permission. Unknown dispatch or missing results must remain separate facts rather than fabricated results.

The factory authenticates neither saved bytes nor caller, performs no implementation-local domain validation, and never obtains a tool, capability or prepared handle. Establish trusted checkpoint/source/target authority independently before using it. Its immutable `IsHistorical` classification distinguishes data from evidence of a current invocation. Integrations must reject imported history at their current-operation result guard; the production runtime does so before accepting a result or advancing the provider. `ProviderInput.FromTool` may carry admitted history as data. Historical results cannot claim a prepared handle, replace current capability checks or manufacture a new invocation charge.

The independently compiled `HistoricalToolResults` consumer and `HistoricalToolResultTests` roundtrip actual guarded success, pre-dispatch rejection, cancellation and post-effect failures, including all supported producer failure codes. Boundary cases reject malformed associations, schemas, encoding, sizes and outcome/error/start combinations. Runtime interface-misuse tests prove a matching historical result cannot substitute for current execution evidence.

The independently compiled [structured read producer](../../../tests/ConsumerProbes/CustomTools/StructuredReadTool.cs) supplies all five nonterminal read-shaped inputs/results with synthetic identity, observation and hash data. A complete 100-line result exceeds the former 128-member cap while fitting a 4096-byte descriptor limit; nested diff lines exercise five payload containers. [Structured context tests](../../../tests/SolusAgent.ContractTests/Runtime/Tools/StructuredToolContextTests.cs) and the [separate-process check](../../../tests/SolusAgent.ContractTests/Runtime/Context/StructuredContextProcessTests.cs) capture and restore all five actual guarded results through production Runtime, preserving raw calls, historical classification and zero repeated tool entries. Malformed nested history and changed range/enum/nullability/item semantics reject before provider import. Shape admission supplies no product identity, cursor, evidence or terminal acceptance.

## Batch admission obligations

Before a batch's first effect, an integration must impose finite count and aggregate byte limits, validate and prepare every member, preserve each original association, reject duplicate call IDs or ambiguous tool binding, verify every required narrow capability, and complete its host-owned admission policy. A rejected member must not be hidden by dispatching earlier members during preparation. The [runtime tool adapter](runtime-tools.md) explicitly implements sequential partial execution with immediate restricted records and no retry or rollback promise. Scheduling, concurrency and run capacities remain runtime responsibilities rather than Tools.Api policy.

The test-only bounded host example prepares all members and checks count, aggregate bytes, distinct IDs and the same generic ValidateInvocation capability guard before any dispatch. Its canary stays zero for valid preparation and for invalid, ambiguous, oversized or unauthorized batch admission. Invocation is always a subsequent explicit operation; no provider retry authorizes retry of tool effects.

## Trusted operation recovery (M4-R2)

`ToolOperation` carries a runtime-created nonempty operation key, the exact original call and an optional `ToolRecoveryBinding`. Runtime supplies the operation before the first possible effect and retains it for subsequent physical attempts. The binding is a trusted Host declaration with a bounded binding ID, actual target snapshot and one closed guarantee: `ConcurrentSafeRepeat` covers repetition even while the original invocation may still be executing; `QueryOutcome` permits retrieving a terminal prior outcome only. `ToolEffect.ReadOnly`, matching names, failures and timeouts provide neither guarantee. Saved binding evidence never supplies a live capability or permission.

`IRecoverableFunctionTool` is optional. `ValidateOperation` must be effect-free and verify current permission, the actual injected target and the exact original operation/guarantee. `InvokeOperationAsync` must preserve the normal concrete capability, owner, exact-call, cancellation and atomic single-use guards; each authorized new physical invocation receives a fresh prepared handle while retaining the original operation key. `QueryOutcomeAsync` performs only the explicitly admitted query. It returns a bounded `ToolRecoveryReceipt`, with exact operation/call association and original outcome/error/started/JSON facts, or unresolved. Unresolved is not evidence of no effect and never grants a repeat. A found terminal failure remains a failure; the query-only route does not turn it into another invocation or a later contradictory success.

Consumers authenticate the live query source and operation/target association, then use the existing `ToolResult.RestoreHistorical` with the original descriptor. The original `InvocationStarted` describes the recovered operation, while the query has its own physical-entry charge. Historical results remain invalid as current invocation evidence. Operation keys, targets, arguments, receipts and exception text are restricted data; the recovery types' `ToString` methods disclose only their type names.

The separately compiled `RecoverableCounterTool` preserves the real `FunctionTool` prepared-handle guard and receives the key before its synthetic effect. Its Host-owned keyed target demonstrates overlapping safe repetition and query-only retrieval, including a bounded test-file target shared by real processes. This is consumer conformance evidence, without a production persistence or crash guarantee. See the [R2 runtime behavior](runtime-tools.md#partial-batch-recovery-r2) and [R2 validation](../../00_project/validation.md#partial-tool-recovery-checks-r2).
