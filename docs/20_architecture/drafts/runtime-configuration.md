# Runtime configuration and exposure draft

`SolusAgent.Runtime.Api.Configuration` and `.Exposure` supply live Host configuration and ordered exposure/closure contracts for the self-owned runtime. The independently compiled [CustomProvider configuration consumer](../../../tests/ConsumerProbes/CustomProvider/RuntimeConfigurationProbe.cs) exercises the M1 shape with actual guarded providers and tools. Its sole direct production reference remains Runtime.Api, with no packages or Runtime dependency. This M1 fixture supplies no production startup or loop evidence. The [runtime execution draft](runtime-execution.md) owns actual provider-turn execution and run-local accounting; the [runtime tool adapter](runtime-tools.md) consumes its captured registry, while the optional [DeepSeek adapter](deepseek-provider.md) owns transport proof. Persistence, automatic retry, recovery and restoration remain later work.

## Authority and support

`RuntimeConfiguration` retains the explicitly Host-installed `IModelProvider`, copied `RuntimeToolRegistration` inventory, optional `IRuntimeExposureHooks`, configuration-specific `ProviderExchangeBounds`, required exposure acknowledgement strength and new `RuntimeGuarantee` requirements. The current immutable `AgentRequest` remains the sole source of run `Bounds`, optional `UsageLimits` and existing `RequiredCapabilities`. Configuration does not duplicate those controls or extend the outer agent API with a mandatory provider/tool registry.

Each registration accepts `IFunctionTool` and an explicitly injected `IToolCapability`. Descriptor/semantic-ID matching associates the binding without certifying concrete capability authority. The real tool owns preparation, full-call/owner association and invocation guards. The actual tests register both a base-derived tool and an interface-only forwarding implementation, invoke their real guarded behavior, and reject a same-ID wrong concrete capability, wrong owner/call and reused invocation before additional effects. Descriptive name, effect or schema metadata never grants authority. The accepted [complete-batch tool admission](provider-exchange.md) remains a separate obligation.

`RuntimeSupport` describes the consuming implementation's existing `AgentCapability` support plus new ordered-exposure and provider-bound guarantees. It is not a Host-selected offer or enforcement certificate. The toy consumer owns a fixed disclosure: Cancellation, UsageReporting and DispatchLimits, plus both runtime guarantees. It rejects required WorkUnitLimit, DurationLimit, UsageThresholds or ToolInvocationLimit before hooks or provider effects. Those optional inputs are advisory when enforcement is not required; the toy does not enforce work, duration, token thresholds or tool invocation allowances. Null `UsageLimits` and individual null dimensions remain valid. Only supplied logical/physical count limits are enforced, with a separate documented eight-attempt fixture capacity. The closed support validator recognizes ToolInvocationLimit independently; the production runtime advertises and enforces it through its [tool adapter](runtime-tools.md).

The registry samples Count once, rejects negative/above-ceiling counts before allocation/indexing, copies the admitted inventory, and rejects null bindings and duplicate ordinal-exact tool names. It fits both the accepted provider ceiling and any lower configured MaximumTools. `CreateRequest` constructs accepted provider values from captured exact scope, copied descriptors and configured bounds; it performs no dispatch. The consumer validates execution/scope, descriptor bindings, provider capability requirements and supplied bounds no looser than configuration before hooks.

Live provider, tool, capability and hook objects belong only to Host integration. Model, repository, tool and saved text cannot select or replace them. `Describe()` projects only numeric configuration limits and closed requirements; restricted types return type-only `ToString()`. Arbitrary serialization of live configuration is unsupported. Ordinary `RuntimeAttemptDiagnostic` carries only attempt GUIDs/ordinal, closed stops/outcomes and observation availability, without scope labels, payloads, credentials, exceptions, continuations or capabilities. Follow the [security boundary](../security-boundary.md).

## Exposure before dispatch

The production Runtime additionally advertises `UsageAccounting`; the M1 configuration consumer retains its narrower disclosure. Current `AgentRequest.UsageLimits.AccountingPolicy` owns numeric estimates, allowances and unknown-usage policy. An active policy requires installed hooks even when configuration selects `RuntimeGuarantee.None`, independently of whether accounting capability was required. The shared execution preflight rejects missing integration before reservation or effects; no-policy optional-hook behavior remains valid. The independently compiled [AccountingHostProbe](../../../tests/ConsumerProbes/CustomProvider/AccountingHostProbe.cs) exercises the extended contract through actual Runtime tests, without adding a Runtime dependency to CustomProvider.

`RuntimeExposure` reuses the exact `ProviderScope` and full `ProviderAttempt`: execution, logical-call and physical-attempt GUIDs and positive attempt ordinal, together with required acknowledgement strength. It is Host exposure intent, not `DispatchExposure.Dispatched` or storage proof. All receipt comparisons cover both scope labels, every attempt field and the requirement without normalization. An equivalent new immutable value can match; an earlier retry receipt cannot.

With accounting active, `RuntimeExposure.Accounting` also carries the immutable current ledger, including this attempt's explicit input/output reservation and derived disposition/balance. Construction requires the current last attempt Reserved and all prior entries finalized. Receipt matching includes the policy and every correlated numeric entry; totals are derived from those entries, so a same-ID receipt with changed amounts or policy cannot authorize dispatch. Reconstructed equal values match independently of object identity. The [usage draft](usage.md#host-accounting-policy-and-authoritative-ledger) defines measurement versus estimate and unknown balance semantics.

`BeforeDispatchAsync` returns a nullable `ExposureAcknowledgement`. Missing, failed, unknown, denied, mismatched or insufficient-strength feedback supplies no dispatch permission. Only coherent Acknowledged/Permit with full association and adequate strength can pass the consumer's final cancellation/admission cut. Failed/Unknown receipts carry no decision or strength; acknowledged Permit requires strength. Absent required hooks reject before work, while a callback returning null is a distinct missing exchange. Exceptions become fixed failures, with no exception text in protocol data.

Volatile acknowledgement is a Host memory claim. Durable acknowledgement asserts that the Host's own durable-exposure condition has been satisfied; this library and the memory-only fixture do not prove persistence. Exposure failure or unknown delivery may coexist with a Host-side record. The provider can still be known NotDispatched because no valid permission reached its admission cut.

The success trace is expose, matching acknowledgement, actual provider effect, then same-attempt settlement. A barrier-held callback leaves the actual effect counter at zero. Caller-token-aware waiting closes pending admission on cancellation even for an uncooperative hook; eventual completion is observed without accepting a late permission. Cancellation after acknowledgement but before the final cut prevents provider invocation. After the cut, cancellation can retain Dispatched and measured usage; it does not establish remote stop or rollback. Trusted in-process hooks/providers are not forcibly interrupted or isolated.

## Closure and retained evidence

`RuntimeSettlement` retains the original exposure, fully associated `UsageAttemptObservation`, prior runtime stop and optional actual `ProviderOutcome`/`ProviderError`. Provider outcome/error are absent when provider exchange was never invoked; such closure is known NotDispatched with unavailable measurement and an explicit admission stop. No Host-only failure is fabricated as a provider failure. The constructor rejects wrong observation identity, incoherent optional outcome/error pairs and phase contradictions. An invoked-provider obtained or normalized outcome can coexist with None, Cancelled or DurationLimit; a pre-admission or non-authorizing exposure stop cannot claim provider invocation. Later settlement-delivery stops and HostStopped never inhabit this prior-state field. Even a known-zero measurement cannot be fabricated for a never-invoked provider.

The consumer checks full observation association before closure. If an interface extension returns another attempt's valid result, that result cannot enter this attempt's output/history. The current invoked attempt retains Unknown dispatch and unavailable measurement with fixed Rejected/InvalidAssociation; Host closure still runs, while the foreign result's original usage stays untouched. Valid guarded results retain their immutable observation before settlement, including rejection, failure or cancellation after real effects. Missing measurement remains unavailable rather than zero, and positive measured usage remains associated with Dispatched.

`AfterAttemptAsync` returns nullable `SettlementAcknowledgement` with the same full exposure association. Only a correlated acknowledged receipt can express Continue or Stop. Missing, failed, unknown or mismatched delivery cannot authorize continuation or retry. A valid Stop blocks future toy admission while preserving earlier facts. Hook acknowledgement is separate from `UsageAccounting` settlement claims: one may be unknown while the other is reported settled.

Active production accounting adds `RuntimeSettlement.Accounting`, the already finalized authoritative snapshot. Its constructor requires unchanged policy/prior entries and a current entry coherent with the final observation; delivery status cannot change it. The Host returns this post-state in `SettlementAcknowledgement.Accounting`, and Runtime uses `Assess(RuntimeSettlement)` to verify both original exposure and post-state contents. Omitting or changing active accounting evidence is a mismatch. Existing no-accounting consumers may continue using the exposure-only constructor/assessment. Host delivery failures do not roll back local settlement, and provider-reported `UsageAccounting` never overwrites Runtime balances. The [transition table](runtime-execution.md#accounting-transition-and-precedence-table) documents cuts, overrun, unknown policy and next-production precedence.

The toy reports closure for every entered exposure callback, including denial/failure/unknown/cancellation. This is its explicit test policy; the universal contract supplies closure expressibility, including acknowledged-then-cancelled NotDispatched and known/possibly dispatched attempts, without requiring every production policy to invoke closure after every exposure failure. A separately Host-controlled settlement token lets cancellation of the run coexist with closure. An uncooperative pending settlement cancelled through that token becomes Unknown delivery; late Continue cannot reopen admission. Independent admission/provider stop and settlement delivery fields prevent later failure from erasing original observations.

Every retry is an explicit caller request with the same logical call, next ordinal and a new physical GUID, repeating exposure/acknowledgement/dispatch/closure. The finite toy inventory rejects reused identities, invalid ordinals, cross-run association and concurrent retries of an active logical call. Count admission includes each new physical attempt. No automatic retry, reservation, global scheduler or restart reconciliation is delivered.

## Synthetic proof and limits

The production [runtime execution draft](runtime-execution.md) adds `RuntimeStop.DurationLimit` for a whole-run local deadline and the required `providerInvoked` constructor argument / `ProviderInvoked` property on RuntimeSettlement. Invocation and obtained-result availability are separate: pending invoked work at Cancelled/DurationLimit may have absent outcome/error with retained known or unknown facts. An actual interface throw or invalid result can be normalized to an observed Failed/Rejected exchange; a pending operation is never fabricated as provider failure. Never-invoked states retain NotDispatched/unavailable observations and an explicit admission stop. Existing consumers and phase validators use this one current draft shape.

The existing runner's `RuntimeConfiguration` tests exercise actual provider/tool effects, held acknowledgement, full association neighbors, durable-required denial, explicit retries, cancellation on both sides of the cut, retained usage despite closure failure, Host Stop, optional controls, bounded registries and safe canary projections. Architecture tests evaluate the unchanged four-library and independent consumer graph; the full suite preserves accepted Execution, Usage, Tools, Candidates, Providers and Context behavior. Use the [project validation commands](../../00_project/validation.md).

The fixture's saved canary view uses the accepted restricted `AgentContextEnvelope` with bounded synthetic data, then receives current live configuration independently. This proves authority/data separation, not a runtime codec or restore round trip. Private synthetic provider/hook/tool credentials stay outside model-visible strings, saved bytes and ordinary projections. Actual transport/parser projection, production enforcement, durable exposure/closure, complete runtime restoration and downstream migration require later M2-M4 work and separate evidence.
