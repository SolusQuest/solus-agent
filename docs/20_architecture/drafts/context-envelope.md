# Context envelope draft

`SolusAgent.Api.Context` expresses implementation-owned restricted state and explicit Host intent through optional `IContextAgent`. An actual producer and Host consumer compile in the existing Api-only library; Context tests run in the existing managed contract runner. The M1 fixture proves admission and restricted access. The production Runtime implements bounded ordinary C1 and completed-tool R1 capture/restoration described below; partial-tool and candidate recovery, provider-specific persistence and arbitrary crash recovery remain separate outcomes.

## Envelope and authority

`AgentContextEnvelope` contains a nonempty `ImplementationId`, positive `FormatVersion` and `CompatibilityVersion` discriminators, and defensively copied opaque bytes. These are implementation-scoped admission metadata, not package support versions, authentication or a portable transcript. Empty or malformed bytes remain representable so the receiving implementation can explicitly reject them. The outer API chooses no provider/model records or universal capacity policy.

The payload has no public property. `CopyRestrictedPayload()` deliberately copies restricted material for authorized admission or Host storage; every call returns a new array. Safe string representations and ordinary envelope serialization expose only structural metadata. An implementation's producer must exclude credentials, transports, live clients, delegates and tool instances from its serialized contents. Arbitrary bytes cannot be authenticated or scanned generically by this outer representation.

Current trusted instructions, bounds, required capabilities and separately classified `AgentInput` come from the current `AgentRequest`. Supplied content remains data and cannot grant tools, change policy, select provider configuration or replace those controls. The Host supplies execution capabilities again and establishes the integrity and authorized origin of the storage/reinjection path. Matching metadata alone is insufficient evidence of provenance. Implementations must validate their own grammar, compatibility and applicable authority before supplied state influences work.

## Intent and admission

`ContextExecutionRequest` requires an explicit intent. `Fresh` has no envelope; `NewRunFromContext` and `ContinueRun` require one. A contradictory shape or undefined intent is rejected before invocation with a safe validation error. Execution correlation does not become a retained-state lookup address or acquire a universal uniqueness/continuity rule.

| Observation | Ordinary work outcome | Meaning |
| --- | --- | --- |
| `Fresh` admission | Same-associated `AgentOutcome` | Fresh work was admitted. |
| `Supplied` admission | Same-associated `AgentOutcome` | Supplied state was admitted for the selected new-run or continuation intent. |
| `NotAttempted` | Zero-work cancellation or required-capability rejection | Current guarantees or caller cancellation prevented context admission. Any supplied usage inventory is complete and empty for this pre-work path only. |
| `Rejected` | None | Supplied state was rejected before work; no work failure is fabricated. |

Closed rejection codes distinguish unsupported context, implementation mismatch, unsupported format, incompatible context, invalid implementation payload and invalid selected transition. The actual fixture checks required guarantees before cancellation, then checks supplied-context support, implementation, format, compatibility, grammar and transition before work, progress or capture. It never calls ordinary execution as recovery from rejection. Starting fresh after rejection requires a separate explicit Host request.

`ContextExecutionResult` contains correlation, intent/admission, a rejection code, nullable truthful work outcome, separate capture status, optional numeric checkpoint identity and separately inspectable historical round observations. Admission does not imply successful work, product acceptance or Host effects. Accepted ordinary Execution and Usage semantics remain unchanged: `ExecutionFailed` describes an actual work-operation failure, not context rejection. Constructors validate coherent structural observations without authenticating their origin.

## Explicit restricted capture

The Host optionally supplies `IRestrictedContextSink` for this invocation, separately from ordinary progress. The implementation documents its capture safe points and transfers an immutable envelope through `Capture`. The sink is a restricted channel; the Host can copy, keep or discard its contents under its own integrity, storage, protection, visibility, retention and deletion policy. This API has no agent-owned per-execution store, extraction by ID, retention duration or post-hoc lookup obligation.

Capture observation is independent of the work outcome. `NotRequested` means no sink was requested; `Unavailable` means no state was transferred; `Delivered` means the callback returned normally; `Failed` means capture failed and may already have delivered state to the Host. None proves durable storage, authenticated integrity, accepted effects or absence of retained bytes. A capture exception is confined to the closed status and cannot rewrite a completed work outcome into an execution failure. Ordinary progress/results and safe strings omit envelopes, payloads and raw exception text. No forced callback liveness or abrupt-process-death result is promised. Checkpoint metadata describes successfully prepared bytes; the ordinary runtime publishes it only after encoding succeeds, including when the subsequent sink fails. `ContextExecutionResult` rejects empty checkpoint identities and malformed historical identity/reason/count/usage fields from any producer. This structural validation does not authenticate provenance or impose execution-ID uniqueness on every `IContextAgent`.

## Actual synthetic evidence

`ScriptedContextAgent` implements the optional interface in the independently compiled Api-only consumer. Its ordinary `IAgent` path delegates to the existing synthetic execution implementation. Its context path uses only call-local state, a newly injected narrow fake work capability and independent ordinary observers/restricted sinks. It transfers one terminal safe-point snapshot for an admitted call when requested, including partial/resource/cancellation/controllable failure stops. Rejected and not-attempted calls transfer nothing. Overlapping calls, including reused correlations, deliver to their own supplied sinks without shared lookup or last-writer-wins state. `RestrictedContextHost` is explicit test-only Host retention outside the ordinary consumer result.

The private toy JSON snapshot contains only an originating correlation, completed synthetic count, synthetic goal, finished marker and copied classified untrusted data. It excludes old trusted instructions, bounds, requested guarantees and live capabilities. Strict UTF-8/field/value admission rejects malformed, missing, duplicate, unknown or contradictory records. This minimized fixture grammar is not the runtime's saved format or restoration codec.

The toy implementation starts fresh at zero. Its supplied new-run policy uses a distinct toy correlation and resets the count; its unfinished continuation policy requires the toy origin/goal and retains completed work under current Host limits. A completed toy snapshot may be explicitly used for a new run. These are private fixture policies used to prove the public distinctions, not universal ID/recovery rules. Newly injected capabilities and current Host controls remain authoritative; prior text stays classified data.

Context tests invoke that actual producer and consumer for every rejection class, explicit intents, no fallback, current control/capability reinjection, exact/below-retained-count bounds, cancellation/work/observer failure, defensive copies, restricted canary confinement, positive capture and independent concurrent sinks. They inspect evaluated project/compiled assembly references and ordinary safe graphs including accepted Usage and closed capability metadata. ## Production ordinary context (C1)

The public factory returns an implementation of `IContextAgent`. Fresh ordinary execution can transfer a terminal safe-point snapshot after completion, resource/deadline/cancellation stops or controlled failure. The version-1 implementation-scoped codec retains classified records, exact accepted Final/continuation associations, per-round usage/accounting, attempt outcome and closure facts, each attempt and Final's original effective request bounds, provider-owned replay state and a numeric checkpoint/cursor. It validates complete constructor-backed fields, UTF-8/JSON, duplicates, unknown fields, identities, ordering, cross-record consistency and finite capacities before admission. R1 extends this codec with tool history below; candidate restoration and provider-specific persistence are separate outcomes.

`ContinueRun`'s ordinary C1 retry route admits only an actual retry-eligible provider failure with known dispatch and acknowledged closure, stopped before its next attempt. It preserves the logical operation, original inputs, exact replay, bounds and increasing global attempt ordinal. Current instructions must match and new input data must be empty. Current retry policy controls the new round. A safely closed accepted Final instead permits `NewRunFromContext`: current instructions replace the old instruction record, new data stays data, accepted model history remains history and a new logical work identity is created. Neither intent replays completed work. Unknown/failed closure, absent Host acknowledgement or uncertain exposure cannot become permission to resume; capture can still preserve those facts. A resumed round stopped during backoff before any attempt preserves its inherited safe pending cursor and replay state for a later authorized round. The codec validates reachable ordinary terminal reason, cut, attempt, closure and Final relationships even when trusted Host evidence matches the bytes. Closure acknowledgement records an actually entered and successfully completed Host closure path; configured hooks alone cannot acknowledge a pre-exposure cut. Accepted Final history is checked against its own original effective bounds and the frozen configuration profile.

Supplied execution requires `ContextRoundGrant`, binding the selected checkpoint, source logical work/round/execution and distinct new execution/round IDs. `RuntimeConfiguration.ContextAuthority` supplies `IRuntimeContextAuthority.TryClaim`: the Host must verify exact metadata and payload against independently trusted evidence, select the current source and exclusively consume both grant and source/round across processes. A hash accompanying untrusted bytes is insufficient. Runtime has no durable registry; a stale snapshot cannot certify absence of later effects. Admission is fail-closed with no fresh fallback. The optional `IProviderContextPersistence` export/import seam is provider-owned and separately bounded, with no dispatch or external storage effects; continuation capability alone does not imply persistence support. Provider-local import/materialization occurs only after the Host verifies and exclusively claims the source. Failed import consumes the grant; missing authority, untrusted bytes and repeated grants never reach import. Live clients, credentials, hooks and tools are reinjected rather than serialized.

Every authorized execution has full current work/count/token/accounting allowances and a fresh duration beginning at resumed execution. Historical observations are returned separately in `History`; current `Outcome.Usage` charges only the new round, including actual retransmitted-history consumption. `UsageCallLineage` links the first new attempt to its exact historical predecessor without renumbering or rebilling old attempts. Automatic retries remain in that round. Retained attempt/record/byte capacities remain cumulative. Encoded checkpoint bytes, current live tool definitions and newly supplied instructions/data occupy retained capacity; a continuation rejects before consuming the grant when capacity cannot preserve its original response bound. Metadata growth can make later capture unavailable without altering the execution outcome. Terminal reason, stop and elapsed duration are frozen before provider export; export delay cannot rewrite completed work.

The independently compiled `PersistentProvider` and `Runtime.Context` tests use public startup and the Api-only context consumer. Real child processes prove positive-usage exhausted-token and partially-used-duration continuations, exact original request/predecessor, fresh budget and no duplicated completed work. Three-process cases preserve pending work through a middle round cancelled or timed out before its first attempt. A fixture-owned trusted selection and flushed exclusive claim files prove rejection of reused grants, competing same-source grants, inconsistent binding and structurally valid tampering across processes. These are controlled producer/Host conformance checks, not a production storage implementation or power-loss durability qualification. The test runner's executable entrypoint exists only to launch these child scenarios; no production executable or dependency is introduced.

Partial tool/candidate state, provider-specific persistence, product recovery policy, storage protection/retention, release support and migration readers remain with their owning later outcomes under [Runtime contract lifecycle](../../00_project/contract-lifecycle.md). No guaranteed snapshot on process kill, arbitrary-instruction recovery, distributed transaction, live provider qualification or downstream product effects are claimed.

## Completed tool history (R1)

The ordinary production codec now retains accepted ToolCalls and their original effective bounds, full normalized descriptors, original raw call arguments, model/member associations, member ordinals, actual result/error/InvocationStarted facts, partial states, committed record positions and an explicit next-provider cursor. It validates reachable mixed model/round history: completed work counts accepted model responses, each subsequent operation follows a completed successful batch or genuine safe retry, original operation ordinals remain intact, and per-round tool interface counts match retained member facts. Saved chronological order is strict even though ProviderRequest permits a complete result collection to be reordered by exact call identity.

`ContinueRun` additionally admits the boundary after acknowledged ToolCalls closure and every successful member result commit, before the next provider effect. It needs no retry policy and never invokes those members again. A genuine provider failure after completed tools uses C1's original retry cursor and immutable effective request bounds, retaining all earlier tool facts. Multiple batches/rounds, closed-Final NewRun and a zero-attempt middle-round cut preserve the same history; current instructions must still match for ContinueRun and new data must be empty. Current work/count/token/accounting/tool allowances and duration renew, while records, members, attempts and retained bytes remain cumulative. A current tool call passes normal preparation, permission, capability and result guards and is counted once.

Before consuming Host authority, deterministic validation includes the complete prospective request payload, current live tool definitions, encoded checkpoint bytes, input/record/member/attempt counts and applicable response reservation. A pending retry reserves its immutable original effective response bound. An exact-capacity request can proceed; one byte less rejects with zero Host claims, provider imports and new effects. Checked accounting is compared with the actual materialized ProviderRequest payload. After the Host independently verifies provenance, current source and actual effect-target compatibility and exclusively claims the source/grant, Runtime reconstructs ToolCalls through `ProviderResponse.RestoreToolCalls` and historical results through `ToolResult.RestoreHistorical`. It then validates the materialized next request and admits provider-owned replay. A remaining semantic or provider-import failure consumes the claim but never dispatches work. No fake preparation, guarded invocation, reflection, current effect or debit is used to regenerate history.

Runtime checks full descriptor/schema/capability semantics against current bindings. The trusted Host must independently establish compatibility of the actual reinjected effect targets: equal descriptors or CapabilityId values cannot identify a target. R1 adds no universal target registry or serialized live authority. The process fixture loads actual Counter/Transform state and independently selected target identities, rejecting a changed target with identical metadata before import/effects. These are Host-conformance fixtures rather than production storage or durability guarantees.

Partial batches retain successful earlier results, actual guarded failure/rejection/cancellation, unstarted members and unknown interface results without inventing outcomes. They have no R1 continuation cursor and cannot replay completed effects; R2 owns recovery. Capture still freezes execution before export, publishes metadata only after successful encoding and reports sink failure separately from work. Candidate restoration and provider-specific composition remain outside this leaf.

Real separate child processes execute independently compiled Counter and interface-only Transform with nonzero effects and positive usage, then restore exact model/call/raw-argument/result/descriptor/replay history with zero additional completed-member entries. Field assertions accompany fingerprints, historical tool counts remain separate from current zero counts, and fresh budgets/duration are exercised. Owning tests also cover trusted structural/semantic corruption, current controls, capacity neighbors, genuine retry after tools, multiple mixed rounds, partial/unknown facts, actual late completion and current-result misuse. See [project validation](../../00_project/validation.md#completed-tool-context-checks-r1) for commands and evidence limits.
