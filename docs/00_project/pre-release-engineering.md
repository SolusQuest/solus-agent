# Pre-release engineering

Before the first supported downstream-consumable release, optimize for learning, correctness, and reversible progress. Apply the minimum process that protects the concrete current failure surface. Pre-release status does not waive privacy, authorization, destructive-operation boundaries, or an actual consumer commitment.

## Default change budget

One independently acceptable outcome ordinarily needs:

- zero or one tracking issue, according to its planning and coordination needs;
- one coherent implementation pull request;
- one review covering related code, contracts, documentation, and validation;
- one maintainer merge decision;
- checks selected from the affected behavior.

An explicitly authorized local initialization can remain uncommitted for maintainer inspection. Do not turn the missing initial commit, issue, or process template into a blocker for that local work.

Keep implementation together with the tests, fixtures, and documentation needed to accept it. Split work when the results are independently useful and acceptable, have independently unblockable dependencies, or require distinct current authority decisions. A coordination parent should add useful dependency or closure information rather than duplicate milestone membership.

## Reuse before invention

Before establishing a durable external contract, persisted format, security mechanism, distribution design, or irreversible workflow authority, inspect a small number of mature comparable systems or standards. Record the adopted pattern and the concrete project constraint behind a material divergence.

This is a bounded design check, not a research gate for routine code, ordinary tests, reversible draft changes, or local refactoring. Reuse only the parts needed for the current boundary; copying code or assets also requires respecting their licenses.

## One current draft

Maintain one current draft contract shape and one production implementation for each selected implementation path. Replace superseded producers, consumers, readers, writers, fixtures, and documentation coherently rather than retaining unreleased compatibility aliases or silent fallback paths.

Intentional agent and model-provider alternatives are supported extension implementations, not obsolete compatibility paths. Synthetic implementations used by tests are also legitimate.

A real external consumer, retained context that cannot be discarded, or an explicit support commitment can require compatibility. Record the affected boundary, why coordinated replacement is insufficient, its owner, lifetime, and removal condition. Possible future users alone do not justify a migration framework.

## Additional process

If a plan introduces extra pull requests, merge stages, independent reviews, repeated full validation, persistent attestations, compatibility machinery, or external mutations, explain briefly:

- the extra stage or mechanism;
- the current failure it prevents;
- why the simpler path is insufficient;
- its removal or simplification condition, when applicable.

Do not require a routine change to fill out a process checklist. Ordinary Git and CI identities normally provide enough development provenance. Introduce additional evidence formats only for an actual transfer or authority boundary they protect.

Validation infrastructure supports the product; it should not become a second certification product. Retire completed experiment machinery while preserving useful regressions and concise historical conclusions.

## Current-owner corrections

Closed work records what was accepted at its historical revision. A later defect belongs to the current failing producer-consumer boundary by default. Preserve historical evidence and make the minimum coherent current-owner correction, including adjacent affected behavior.

Combine recurring failures at the same boundary rather than creating one correction ceremony per assertion. Reopening closed scope, changing product semantics, or expanding an external authority requires the corresponding maintainer decision.

Reuse evidence for unchanged inputs. After a correction, review and validate the affected behavior without restarting unrelated work. A timeout, cancellation, or incomplete run is not a pass or permission to retry until green.
