# Internal package release

The `Internal release` workflow publishes the five SolusAgent packages at one explicit `0.1.0-internal.N` version. An authorized maintainer's manual dispatch on `main` is release authorization. Other events or refs fail. One checkout binds the dispatch SHA, disables persisted checkout credentials, and uses managed .NET 10 on Ubuntu 24.04 x64 with Node 24. The workflow restores, builds and tests, packs once, then validates the same local archives with `--scenario all --require foundation,apr,scribe,smoke-offline`. Missing or unselected required scenarios fail before any upload. No live smoke, provider secret, candidate approval, environment approval or promotion step belongs in this workflow.

## Private access prerequisite

Before enabling publication, a maintainer must inspect actual GitHub organization and package settings. For new identities, permit private creation and disable **Organization Settings → Packages → Default Package Settings → Inherit access from source repository**. For existing identities, require private visibility, disabled inherited permissions, intended users/teams and the publisher's intended Actions write access. Review public-repository Actions access carefully: GitHub warns that forks may be able to access packages granted to a public repository. Establish only intended access, including later explicitly granted consumer repositories. Do not publish first and repair permissions afterward.

After verifying those actual settings, the maintainer may maintain the repository or organization configuration variable `SOLUS_INTERNAL_PACKAGE_ACCESS=private-no-inheritance`. It is unset by default and any other value prevents the first push. This is persistent operational configuration, not a per-dispatch approval input and not proof from a live API. Reverify before dispatch and after access/settings changes; clear it whenever the prerequisite is no longer established. A stale assertion is an operational risk. Setting changes and first-release access qualification are separate authorized operational work, not performed by engineering validation.

GitHub NuGet defaults new packages to private visibility, but visibility alone does not prove effective inherited or Actions access. The documented REST API exposes readable package metadata and versions, not the organization/package inheritance configuration. Caller-visible inventory is not an organization-wide proof of nonexistence. The trusted settings prerequisite therefore remains separate from API checks. Publication preflight requires authenticated metadata pagination to finish, existing identities to be private NuGet packages, and both the selected version and tag to be absent. Unknown, inaccessible or failed checks stop before any push; the registry independently rejects racing version conflicts.

See GitHub's [NuGet authentication and linkage](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-nuget-registry) and [access/visibility controls](https://docs.github.com/en/packages/learn-github-packages/configuring-a-packages-access-control-and-visibility). Consumers need explicit package read access. The shared runner uses existing `GITHUB_TOKEN` plus an explicit `GITHUB_ACTOR` account for automatic GitHub NuGet authentication; local PAT use requires the actual token owner's account. It never invents a username, creates a token or writes credentials to source. An explicit `NuGetPackageSourceCredentials_selected` remains supported.

## Dispatch and failure handling

Choose a fresh canonical version and dispatch `Internal release` from `main` with that version. The selected source SHA is checked against the actual checkout. Only the authenticated preflight/upload/tag step receives `GITHUB_TOKEN`; the job grants only contents/packages write scopes. Offline preparation receives no publication credentials, and checkout does not retain authentication in Git configuration. The five inspected `.nupkg` paths are uploaded directly from the validated directory; there is no second pack, checkout or artifact reconstruction. The lightweight `v<version>` tag is created through the GitHub API at the selected source SHA only after all five uploads succeed.

Any existing package version or tag rejects reuse. Uploads do not skip duplicates, force replacement or delete packages. An interrupted or failed upload can leave a partial version set; the failure reports known successful IDs and the failed/unknown package and creates no success tag. A tag failure after five successful uploads is also a failed run. Inspect the original operation before recovery, retain its outcome honestly, and choose a new internal version. Do not replay an ambiguous push or tag automatically. Publication is serialized without cancelling an active release, but metadata preflight cannot eliminate external races.

## Engineering validation

Use the normal solution restore/Release build/full test commands and the package positive/negative commands in [project validation](../00_project/validation.md). Run `node --test scripts/packages/selection.test.ts scripts/release/release.test.ts` and `actionlint .github/workflows/release.yml` for focused deterministic helper/workflow checks. The test's YAML inspection uses the existing Ruby standard library; the release runtime remains native TypeScript without package-manager bootstrap. These checks inject synthetic registry/upload/tag operations and never create tokens, dispatch workflows, publish packages, mutate settings or execute live smoke.

The credential-free helper is `node scripts/release/prepare.ts --version <version> --output <fresh-directory>` in the selected dispatch context. It invokes the existing pack command exactly once, then the same shared consumer runner with all four required offline aliases. While APR, Scribe or smoke-offline are absent, the required-set negative is valid engineering evidence and actual preparation remains blocked. It is never acceptable to relax the required set to make a release pass. Actual dispatch, all-five registry readback, private access proof and authenticated clean consumption belong to the separately authorized first-release work.

The shared manifest retains `projects` and `entrypoints`, with optional `aliases` naming safe zero-argument defaults. A scene can additionally own `liveAlias: "smoke-live"` and `liveProfile: "deepseek-flash-thinking-high"`. `all` executes only defaults. The live alias requires exclusive explicit selection, `--live`, an absolute ignored regular local key file outside every copied scene source root and the supported profile; it is rejected in CI or with any other scenario. Only that path forwards `smoke-live --live --key-file <path> --profile deepseek-flash-thinking-high`. The runner checks metadata/ignore status without loading key contents and suppresses raw entrypoint failure output. The smoke executable repeats its own authorization/profile/key gates. This interface does not authorize a live run.

Internal identities are immutable and consumers pin versions. No upgrade compatibility is promised before formal release, including saved context. This workflow does not establish public licensing, product migration, Native AOT or broader platform qualification.
